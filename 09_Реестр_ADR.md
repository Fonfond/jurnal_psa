## ADR-01. IndexedDB как источник истины на клиенте

| Поле | Значение |
|---|---|
| Проблема | Нужен офлайн-доступ к записям, справочникам, очереди и черновикам без сети |
| Альтернативы | Кэш API-ответов в Cache Storage; SQLite через WASM; OPFS |
| Решение | IndexedDB — единственный источник истины; Cache Storage только для статики и модели ASR |
| Обоснование | Стандарт, транзакции, индексы, поддержка во всех целевых браузерах, зрелые библиотеки |
| Плюсы | Атомарность, запросы по индексам, объём, предсказуемость |
| Минусы | Асинхронный API, риск вытеснения, нет шифрования |
| Влияние | Синхронизация, поиск, миграции |
| Статус | Согласовано |

## ADR-02. Честная модель гарантий + экспорт и бэкап

| Поле | Значение |
|---|---|
| Проблема | v1.0 обещала «RPO=0 при любых сценариях»; браузер этого не гарантирует |
| Альтернативы | Оставить обещание; перенести хранение в нативное приложение; облачный буфер |
| Решение | Гарантии ограничены штатными сценариями; 9 механизмов защиты (M-01…M-09); экспорт аварийной копии; индикатор риска |
| Обоснование | Юридическая и репутационная честность; управление ожиданиями |
| Плюсы | Нет ложных обещаний; пользователь видит риск и может сохранить копию |
| Минусы | Часть пользователей воспримет как «ненадёжно»; нужен UX-объяснение |
| Влияние | UI, поддержка, KPI-04 |
| Статус | Согласовано |

## ADR-03. Единый путь записи через `/sync/push`

| Поле | Значение |
|---|---|
| Проблема | Два пути записи (REST и очередь) создают расхождения и дубли |
| Альтернативы | REST для онлайн, очередь для офлайн; отдельные endpoint’ы на каждую мутацию |
| Решение | Все мутации PWA — через `POST /sync/push`; REST — только онлайн-операции руководителя/админа |
| Обоснование | Один код-путь, одна идемпотентность, один аудит |
| Плюсы | Проще тестировать, меньше расхождений |
| Минусы | REST-мутации админа отдельно; нужна дисциплина |
| Влияние | API, синхронизация, аудит |
| Статус | Согласовано |

## ADR-04. Серверный авторитетный field-merge

| Поле | Значение |
|---|---|
| Проблема | Не определено, кто и как сливает версии при 409 |
| Альтернативы | Клиентский merge; блокировка записи; CRDT |

| Плюсы | Детерминизм, защита от подмены, проще клиент |
| Минусы | Сложнее сервер; нужен G3-прототип |
| Влияние | Sync, ConflictRecord, API |
| Статус | Согласовано |

## ADR-05. HLC фиксированной ширины + защита от дрейфа

| Поле | Значение |
|---|---|
| Проблема | Строковое сравнение HLC ломалось; скачок часов отравлял порядок |
| Альтернативы | Lamport clocks; серверные версии; NTP-принуждение |
| Решение | Формат 13+5+8; дрейф > 5 мин → `clock_anomaly`, серверный порядок |
| Обоснование | Лексикографический порядок = хронологический; устойчивость к неверным часам |
| Плюсы | Простая сортировка, защита от аномалий |
| Минусы | Дополнительное поле в аудите |
| Влияние | Все сущности, аудит |
| Статус | Согласовано |

## ADR-07. Tombstone 90 дней + полная пересинхронизация

| Поле | Значение |
|---|---|
| Проблема | Удалённые записи «воскресают» после долгого офлайна |

| Влияние | Sync, БД |

## ADR-10. «Блокировка» и «выход с очисткой» разделены

| Поле | Значение |

| Альтернативы | Блокировать выход; очищать всегда |

| Обоснование | Безопасность и сохранность одновременно |
| Плюсы | Смена пользователя, данные не теряются |

| Влияние | Auth, UI, хранилище |
| Статус | Реализовано (t10): `lock()` закрывает БД без удаления, `logout()` удаляет базу пользователя; офлайн-разблокировка — AUTH-03 |

## ADR-21. PGlite для локальной разработки и тестов

|---|---|
| Проблема | В окружении разработки нет Docker и PostgreSQL-сервера, а код должен запускаться и тестироваться локально |

| Влияние | DbModule, миграции, тесты, документация запуска |
| Статус | Принято; реализовано (PGlite local/test, PostgreSQL production) |

## ADR-23. OIDC Authorization Code + PKCE и регистрация устройств

| Поле | Значение |
|---|---|
| Проблема | Dev-провайдер не годится для production; `auth/authorize|callback` были `501`; не было регистрации устройств и привязки сессии к устройству |
| Альтернативы | SAML; собственный IdP; OIDC-библиотека (jose/openid-client); минимальный OIDC-клиент на `node:crypto` |
| Решение | `IdentityProvider` как шов: `dev` (ADR-22) и `oidc` (Authorization Code + PKCE S256, `state`/`nonce`, discovery, JWKS-проверка `id_token`); логин-транзакции в `oidc_login_requests` + HttpOnly cookie; сопоставление по `(issuer, subject)` → подтверждённый email → опциональный JIT; `POST /v1/devices` по `install_id`, одноразовый `device_key`, привязка сессии и каскадный отзыв |
| Обоснование | Стандартный SSO без внешних зависимостей; production-гейты fail-closed; сохранён локальный dev-вход; устройство становится границей доверия для offline-first |
| Плюсы | Нет JWT-библиотек в зависимостях, полный контроль проверки токена; MFA — политикой IdP; отзыв устройства инвалидирует его сессии |
| Минусы | OIDC-клиент нужно сопровождать (алгоритмы, JWKS-кэш, discovery); нет самостоятельной регистрации — пользователей создаёт администратор |
| Влияние | `apps/api/src/auth/**`, `devices/**`, миграция 0007, `.env`, web-экран входа и sync-bootstrap |
| Статус | Принято и реализовано; интеграция с реальным IdP — после OQ-02 |

## ADR-25. Абстракция электронной подписи (simple/qualified)

| Поле | Значение |
|---|---|
| Проблема | OQ-04 не закрыт, но визы и проверки журнала должны иметь проверяемую целостность и быть готовыми к КЭП |
| Альтернативы | Не подписывать; сразу КЭП; хранить только hash/audit; адаптеры с переключением |
| Решение | `SignatureProvider` + адаптеры `none`, `simple` (HMAC-SHA256 сервера), `qualified` (HTTP к сервису КЭП, CMS + сертификат); подписи в `document_signatures` привязаны к версии и каноническому хэшу; оговорка «не КЭП» в каждом ответе и CSV; авто-подпись только для in-process `simple` |
| Обоснование | Целостность уже сейчас, юридическая модель — после OQ-04 без переписывания домена |
| Плюсы | Единый контракт для виз и проверок; проверка подписи по актуальному содержимому; нет private keys в Logbook |
| Минусы | `simple` не является ЭП юридически; `qualified`-адаптер не проверен на реальном сервисе; ротация ключа инвалидирует старые подписи |
