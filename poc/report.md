## 1. Итоговые вердикты

| Гейт | Вердикт | Основание | Что это значит |
|---|---|---|---|
| **G1 — on-device ASR** | **fail (blocked)** | Нет модели ≤ 40 МБ, нет аудиокорпуса 2 ч, нет устройств D1–D7. Стенд честно вернул `blocked`; 12 сценариев не выполнены | Голосовой сценарий нельзя подтвердить. До отдельного прогона — только ручной ввод/Web Speech (при OQ-10); ASR не заявлять |
| **G2 — IndexedDB, квоты, сохранность** | **partial** | На desktop Chromium (D6, headless Edge 158) пройдены атомарность 100/100, 20 перезапусков с 10 000 операций, экспорт/восстановление 4/4, миграция 10/10 с откатом, Web Locks 4/4. Не проверены iOS, реальное вытеснение, `QuotaExceededError`, 80% квоты; `persist()` = false | Механика хранения работоспособна на desktop. Для field-пилота нужны D1–D7, установленное PWA и проверка квоты/iOS |
| **G3 — синхронизация и merge** | **pass (isolated prototype)** | 24 сценария × 20 рандомизированных прогонов (детерминизм — 100), 560 строк, 0 потерь, HLC/seq/идемпотентность/батчи без ошибок, HTTP push 50 ops p95 = 5,26 мс | Алгоритм merge/HLC/идемпотентности жизнеспособен в изолированном прототипе. **Решение:** этап 2 может стартовать в ручном режиме. G3-протокол валидирован на прототипе; G2 требует device-прогона; G1 остаётся fail до появления модели/корпуса/устройств. Продуктовый G3-код (уже существующий) требует отдельной приёмки на PostgreSQL и реальном транспорте — результаты этого отчёта её не заменяют.

## 3. G1 — on-device ASR

### 3.1. Что проверено

Стенд `poc/g1/harness.html` выполняет:

- проверку окружения: secure context, `getUserMedia`, `AudioContext`, `Worker`, `WebAssembly`;
- проверку чанкера 20 с / перекрытие 2 с на синтетическом PCM 120 с;
- проверку наличия модели по `?model_url=`.

Фактический результат headless-прогона:

| Проверка | Результат |
|---|---|
| Secure context | true |
| `navigator.mediaDevices.getUserMedia` | true |
| `AudioContext` | true |
| `Worker` | true |
| `WebAssembly` | true |
| URL модели | отсутствует |
| Чанкер 120 с | 6 чанков + 1 остаток (flush); 320 000 сэмплов на чанк, перекрытие 32 000 |
| Статус | **blocked** |

`poc/results/g1_measurements.csv` содержит 12 строк (по одной на POC-G1-01…12). Числовые метрики в них `n/a`, `notes` = `BLOCKED: not executed`, потому что замеров не было. Это не подмена результата: гейт **не пройден**.

### 3.2. Почему fail, а не partial

По `17_Чек-лист_приёмки_PoC_D10.md` §6.1: `pass` невозможен при отсутствии обязательного сценария; неполный PoC — это `fail` по процедуре. Нет ни одной реальной строки RTF/WER/памяти/iOS, поэтому технический вывод об ASR сделать нельзя. Единственный корректный вердикт — **fail (blocked)**.

### 3.3. Что нужно для повторного прогона

1. Модель ≤ 40 МБ с лицензией и SHA-256 в `artifacts.csv`.
2. Аудиокорпус 2 ч (3 диктора, 70/80/90 дБ, 0,3/0,5/1,0 м) и транскрипты.
3. D1–D7 по `12_План_PoC_Этап1.md` §3.1.
4. Прогон POC-G1-01…12 по 5 повторов, CSV с RTF/WER/памятью/крашами.
5. Отдельное решение по iOS и классу C.

## 4. G2 — IndexedDB, квоты и сохранность

### 4.1. Фактические прогоны

`poc/results/g2_measurements.csv` — **153 строки**, 12 сценариев. Все прогоны — desktop Chromium (D6), `data_loss=false`.

| Сценарий | Строк | Фактический результат |
|---|---:|---|
| POC-G2-01 `persist()` | 3 | `persist()` / `persisted()` = **false** (headless, без user gesture); отказ зафиксирован в `notes` |
| POC-G2-02 квота | 1 | **BLOCKED**: реальное заполнение не выполнялось; оценка квоты 10 240 МБ |
| POC-G2-03 атомарность | 100 | **100/100**: commit и forced abort без частичных состояний |
| POC-G2-04 20 перезапусков | 20 | **20/20** с 10 000 операций; потерь нет; открытие 0–1 мс |
| POC-G2-05 экспорт/восстановление | 4 | **4/4**: 10 000 записей и 10 000 операций восстановлены полностью |
| POC-G2-06 очистка данных | 3 | **3/3**: после удаления БД и reopen записей 0 |
| POC-G2-07 вытеснение | 1 | **BLOCKED**: ОС-вытеснение не воспроизводится; только документальное поведение |
| POC-G2-08 iOS | 1 | **BLOCKED**: нет Safari/iOS D4/D5/D7 |
| POC-G2-09 миграция 10 000 | 10 | **10/10**: успешная v1→v2 с backup + откат при сбое; данные целы |
| POC-G2-10 Web Locks | 4 | **4/4**: один из двух конкурентных запросов получает lock; дублей нет |
| POC-G2-11 80% квоты | 1 | **BLOCKED**: в прототипе нет продуктового индикатора |
| POC-G2-12 время открытия | 5 | **5/5** с 10 000 записей; 0–1 мс в headless-профиле |

### 4.2. Вердикт partial

Основания:

- атомарность, перезапуски, экспорт/восстановление и миграция **не теряют данные** на desktop;
- `persist()` не выдан, `QuotaExceededError` не воспроизведён;
- iOS, реальное вытеснение и 80% квоты не проверены;
- 153 строки вместо ≥160 по чек-листу: часть сценариев заблокирована, а не «добита» фиктивными строками.

Ограничение для пилота: **только установленное PWA**; на iOS — предупреждение и запрет записи в браузере до отдельной проверки; контроль квоты и автоочистка кэшей — в остаток (см. `24_Остаток_разработки.md`).

## 5. G3 — синхронизация и merge

### 5.1. Фактические прогоны

`poc/results/g3_runs.csv` — **560 строк**:

- C-01…C-12: по 20 рандомизированных прогонов (порядок доставки, дубли) — 240 строк;
- POC-G3-13…24: по 20 (детерминизм — 100) — 320 строк;
- `deterministic=false` — **0**; `data_loss=true` — **0**.

| Сценарий | Результат |
|---|---|
| C-01…C-12 | 12/12 корректно, 0 потерь, расхождений нет |
| POC-G3-13 HLC | 1 000 пар × 20; mismatches = 0 |
| POC-G3-14 дрейф | +1 ч / −1 ч / +1 год; 60/60 `clock_anomaly`, назад не идёт |
| POC-G3-15 `change_log.seq` | 1 000 изменений, страницы 100, gaps = 0, duplicates = 0 |
| POC-G3-16 идемпотентность | 5 повторов = 1 результат, 80/80 duplicate |
| POC-G3-17 порядок create+update | 20/20 final text = update |
| POC-G3-18 параллелизм 3 сущностей | 20/20 без clobber |
| POC-G3-19 частичный сбой | 20/20: независимые применены, зависимые rejected |
| POC-G3-20 обрыв после apply | 20/20 retry duplicate, второй записи нет |
| POC-G3-21 401 | 20/20 очередь цела, после входа доставлено |
| POC-G3-22 tombstone + полный resync | 20/20 delete виден в changes |
| POC-G3-23 детерминизм | 100/100 один итоговый state |
| POC-G3-24 HTTP 50 ops | p95 **5,26 мс**, max 26,23 мс (localhost, in-memory) |

### 5.2. Вердикт pass для прототипа

Все критерии `17` §6.4 для прототипа выполнены: 12/12 конфликтов, детерминизм 100/100, HLC без аномалий, идемпотентность 100%, порядок батчей, `seq` без пропусков, p95 ≤ 400 мс. **Важно:** это изолированный in-memory прототип, а не продуктовый API, PostgreSQL, auth или реальный сетевой транспорт. Для продуктового G3 нужна отдельная приёмка (PostgreSQL, p95 на стенде, 401-восстановление на реальном клиенте).

## 7. Влияние на этапы и KPI

| Гейт | Влияние |
|---|---|
| G1 fail | Голосовой ввод в пилоте — только ручной/Web Speech (при OQ-10); KPI-01 для on-device не заявляется; ASR — отдельная итерация после модели/корпуса |
| G2 partial | Пилот — только установленное PWA; iOS — предупреждение; квота/вытеснение — отдельный device-прогон |
| G3 pass | Протокол merge/HLC/идемпотентности можно развивать; продуктовый G3-код уже есть, но требует PostgreSQL/транспортной приёмки |

**Матрица решения:** G1 fail + G2 partial + G3 pass → этап 2 стартует в ручном режиме; этап 4 не блокируется результатом G3, но продуктовая реализация G3 проверяется отдельно; G1 не считается пройденным.

## 8. Воспроизведение

```powershell
# G1: harness outputs blocked JSON and writes 12 blocked rows
node poc/tools/run-g1.mjs

# G2: starts static server + headless Edge CDP, writes 153 rows
node poc/tools/run-g2.mjs

# G3: 24 scenarios, 20 runs each (determinism 100), writes 560 rows
node poc/g3/run.mjs

# standalone G3 HTTP server (optional)
node poc/g3/server.mjs
```

Проверки результатов:

```powershell
node poc/tools/validate-results.mjs
```
