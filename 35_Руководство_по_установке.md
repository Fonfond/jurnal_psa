## 1. Что разворачивается

Logbook — три артефакта и одна база данных. Приложение не содержит встроенного веб-сервера для SPA и TLS: статика отдаётся reverse proxy, API работает по HTTP на loopback.

| Компонент | Артефакт | Порт | Примечание |
|---|---|---|---|
| API | `apps/api/dist/main.js` (Node.js) | 3001 (loopback) | REST `/v1`, sync/merge, аудит, PDF, экспорт |
| Web (PWA) | `apps/web/dist` (статика) | 443 через nginx | SPA, service worker, офлайн-очередь |
| БД | PostgreSQL 15 | 5432 (только от API) | PGlite — только локально/тесты |
| Reverse proxy | nginx / IIS / LB | 443 | TLS, SPA fallback, прокси `/v1` |

```
Браузер ──HTTPS──> nginx :443 ──HTTP loopback──> API :3001 ──TLS──> PostgreSQL :5432
                      │
                      └── статика apps/web/dist (SPA + service-worker.js)
```

Рекомендуемая топология имён:

| URL | Что отдаётся | Комментарий |
|---|---|---|
| `https://logbook.example.com` | операционная SPA + `/v1` (прокси) | основной origin (`CORS_ORIGIN`) |
| `https://admin.logbook.example.com` | admin-сборка SPA + `/v1` (прокси) | отдельный origin (`ADMIN_ORIGIN`, ADR-14) |
| `http://127.0.0.1:3001/v1` | API | наружу не публикуется |

Обе SPA обращаются к API через свой origin, поэтому cookie-сессия остаётся host-only и у админки отдельная (ADR-14). API не умеет TLS — не выставляйте порт 3001 в интернет.

| Вариант | Когда | Состав | Статус |
|---|---|---|---|
| A. Windows, один хост | пилот, демонстрация, небольшой объект | Node + PostgreSQL 15 (установщик или `scripts/pg/bootstrap-pg15.ps1`) + nginx/IIS | ✅ лабораторно |

Во всех вариантах: одна и та же схема БД (`db/migrations`), один и тот же production-бандл `apps/web`, одинаковые переменные окружения (§5).

## 4. Подготовка дистрибутива

### 4.1. Состав каталога

```
apps/api            API (src, assets/OpenSans-Regular.ttf, dist после сборки)
apps/web            SPA (dist после сборки: index.html, assets/, service-worker.js, manifest)
packages/shared     общие типы/Zod/HLC/seed-данные (dist нужен API в рантайме)

docker-compose.yml  PostgreSQL primary + replica (профиль ha)
.env.example        шаблон конфигурации
```

### 4.2. Сборка

```bash
npm ci                 # воспроизводимая установка по package-lock.json
npm run build          # shared + api + web
npm run typecheck      # опционально: проверка типов перед выпуском
npm test               # опционально: полный прогон тестов (нужны dev-зависимости)
```

Артефакты выпуска:

| Артефакт | Что копировать на сервер |
|---|---|
| API | `apps/api/dist`, `apps/api/assets`, `apps/api/package.json`, `packages/shared/dist`, `packages/shared/package.json`, `package.json`, `db/migrations`, `node_modules` |
| Web | каталог `apps/web/dist` (в nginx root) |
| Документация | `README.md`, `RUNBOOK.md`, этот документ, `db/postgres/README.md` |

`package.json` в корне нужен API: по нему код находит корень репозитория (`findRepoRoot`) и читает `db/migrations` и `.env`. Если каталог `db/migrations` вынесен, задайте `MIGRATIONS_DIR` (§5.4).

> ⚠ Не копируйте в выпуск `.env`, `.data/`, `db/postgres/certs/`, `poc/`, `demo/`: секреты и локальные данные не должны попадать в артефакт.

## 5. Конфигурация

### 5.1. Где читается конфигурация

1. Процесс читает файл `.env` в корне репозитория (`dotenv`, без перезаписи уже заданных переменных).
2. Другой файл: `ENV_FILE=/etc/logbook/logbook.env` (удобно для systemd/секретов вне каталога). Указывайте **абсолютный** путь: относительный разрешается от текущего каталога процесса.
3. Переменные процесса имеют приоритет над `.env` — в systemd/Docker задавайте окружение через `EnvironmentFile`/`env_file`.
4. Валидация fail-closed: при неверной конфигурации API не стартует и печатает `Invalid environment configuration: <поле>: <причина>` (§5.6).

Файл `.env` не коммитится (`.gitignore`), права — `600`, владелец — служебная учётная запись.

### 5.2. Профили

| Профиль | БД | Аутентификация | Seed | Назначение |
|---|---|---|---|---|
| dev/demo | PGlite (`.data/pglite`) | `AUTH_PROVIDER=dev` | да | разработка, демонстрация |
| pilot | PostgreSQL 15 + TLS | `oidc` (или `dev` с письменным допуском) | нет (только справочники и bootstrap-админ) | контролируемый пилот |
| production | PostgreSQL 15 + TLS | `oidc` только | нет | промышленная эксплуатация |

### 5.3. Production-профиль (проверен валидатором)

```env
NODE_ENV=production
PORT=3001

# --- PostgreSQL 15 (обязательно; без DATABASE_URL API уйдёт в PGlite) ---
DATABASE_URL=postgres://logbook:<пароль>@db.internal:5432/logbook
DATABASE_SSL_MODE=verify-full
DATABASE_SSL_CA_PATH=/etc/logbook/db-ca.pem
DATABASE_POOL_MAX=10
RUN_MIGRATIONS_ON_START=true

# --- Сессии и origin ---
COOKIE_SECRET=<64 hex>
SESSION_TTL_DAYS=30
CORS_ORIGIN=https://logbook.example.com
ADMIN_ORIGIN=https://admin.logbook.example.com

# --- OIDC (ADR-23) ---
AUTH_PROVIDER=oidc
DEV_LOGIN_ENABLED=false
OIDC_ISSUER=https://idp.example.com/realms/logbook
OIDC_CLIENT_ID=logbook
OIDC_CLIENT_SECRET=<секрет клиента>
OIDC_REDIRECT_URI=https://logbook.example.com/v1/auth/callback
OIDC_POST_LOGIN_REDIRECT=/
OIDC_DISPLAY_NAME=Корпоративный IdP
OIDC_SCOPES=openid profile email
OIDC_ALLOWED_ALGORITHMS=RS256
OIDC_REQUIRE_MFA_FOR_ADMIN=true
OIDC_MFA_ACR_VALUES=mfa
OIDC_JIT_PROVISION=false

# --- ЭП (OQ-04): simple = HMAC сервера, не КЭП ---
SIGNATURE_PROVIDER=simple
SIGNATURE_SECRET=<64 hex>
SIGNATURE_KEY_ID=logbook-prod-v1
SIGNATURE_AUTO_SIGN=true

# --- PDF наряда и WORM-экспорт ---
PERMIT_PDF_SECRET=<64 hex>
PERMIT_PDF_TTL_SECONDS=900
PERMIT_PDF_PUBLIC_BASE_URL=https://logbook.example.com
EXPORT_SIGNING_SECRET=<64 hex>
EXPORT_URL_TTL_SECONDS=900
EXPORT_PUBLIC_BASE_URL=https://logbook.example.com
RETENTION_YEARS=3

# --- Видимость нарядов (FR-PRM-11) ---
PERMIT_VISIBILITY_MODE=participant
```

> **ЭП и IdP.** `SIGNATURE_PROVIDER=simple` — HMAC сервера, **не КЭП**.
> `SIGNATURE_PROVIDER=qualified` требует внешний аккредитованный сервис КЭП:
> контракт — `docs/security/QUALIFIED_ES_CONTRACT.md` (sign/verify/error/timeout,
> тестовый HTTP-провайдер только для тестов). `OIDC_REQUIRE_MFA_FOR_ADMIN=true`
> обязателен в production (NFR-SEC-02): без `acr`/`amr` администратор получает
> `E-OIDC-04`. Интеграционный harness и redirect URI — `docs/security/OIDC_INTEGRATION.md`.
> Реальные credentials IdP/КЭП — внешние блокеры OQ-02/OQ-04
> (`docs/security/REP-01_02_WAIVER.md`), mock не выдаётся за production.

Дополнительно для web (`VITE_*` вшиваются **на этапе сборки**, §5.7):

```env
VITE_API_URL=/v1
VITE_APP_VERSION=0.2.0
VITE_ENABLE_DEV_LOGIN=false
# только для отдельной admin-сборки:
# VITE_ADMIN_ORIGIN=https://admin.logbook.example.com
```

### 5.5. Секреты

Генерация (Linux/macOS):

```bash
openssl rand -hex 32   # COOKIE_SECRET, SIGNATURE_SECRET, PERMIT_PDF_SECRET, EXPORT_SIGNING_SECRET
```

Windows (PowerShell 7, криптостойкий генератор):

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
($bytes | ForEach-Object { '{0:x2}' -f $_ }) -join ''
```

| Секрет | Ротация | Последствия |
|---|---|---|
| `COOKIE_SECRET` | 90 дней / при инциденте | все сессии становятся недействительны (пользователи входят заново) |
| `SIGNATURE_SECRET` | **не ротировать без плана** | проверка ранее выданных `simple`-подписей сломается (HMAC-ключ меняется); храните ключ и `SIGNATURE_KEY_ID`, ротация — с перевыпуском подписей или через `qualified` |
| `PERMIT_PDF_SECRET`, `EXPORT_SIGNING_SECRET` | 90 дней | «просроченные» выданные ссылки перестают работать (TTL ≤ 900 с, некритично) |
| `OIDC_CLIENT_SECRET` | по политике IdP | вход через IdP недоступен до обновления секрета |
| `DATABASE_URL` (пароль) | 90 дней | перезапуск API с новым паролем; пароль БД меняется через `ALTER ROLE` |

Секреты храните в secret-manager/файле с правами `600`; в репозиторий и в образ не включайте.

### 5.6. Production-гейты (fail-closed)

`env.ts` не даёт запустить `NODE_ENV=production`, если:

- `AUTH_PROVIDER != oidc`;
- `DEV_LOGIN_ENABLED=true`;
- `COOKIE_SECRET` — dev-значение или короче 32 символов;
- `CORS_ORIGIN` не https (кроме localhost);
- `ADMIN_ORIGIN` не https или совпадает с `CORS_ORIGIN`;
- `DATABASE_URL` не задан (PGlite/память запрещены в production);
- `DATABASE_URL` указывает на внешнюю БД, а `DATABASE_SSL_MODE=disable`;
- `DATABASE_SSL_MODE=verify-full`, но не задан `DATABASE_SSL_CA_PATH`;
- `SIGNATURE_PROVIDER=simple` без секрета ≥ 32 символов;
- `SIGNATURE_PROVIDER=qualified` без endpoint/token;
- `AUTH_PROVIDER=oidc` без `OIDC_ISSUER`/`OIDC_CLIENT_ID`/`OIDC_REDIRECT_URI`;
- `OIDC_JIT_PROVISION=true` без `OIDC_JIT_DEPARTMENT_ID`;
- `OIDC_REQUIRE_MFA_FOR_ADMIN=false` (NFR-SEC-02: MFA администратора обязательна).

Проверено 25.11.2026: production-пример §5.3 проходит валидацию; негативные кейсы
(включая отсутствие `DATABASE_URL`) отклоняются с ожидаемым сообщением.

> `DATABASE_URL` обязателен в production: без него API завершает старт с
> `Invalid environment configuration: DATABASE_URL: production требует DATABASE_URL`.
> PGlite/память остаются допустимы только для локального запуска (`NODE_ENV=development|test`).
> После запуска дополнительно проверяйте `GET /v1/health` → `db=ok` — это подтверждает
> подключение к PostgreSQL, а не к PGlite.

### 5.7. Переменные web

`VITE_*` подставляются Vite **при сборке**, а не при запуске. Изменение `VITE_API_URL`/`VITE_ADMIN_ORIGIN` требует пересборки `apps/web` и публикации нового `dist`. `VITE_ADMIN_ORIGIN` задаётся только для отдельной admin-сборки (ADR-14); если он не совпадает с origin, на котором открыта админка, редирект `/` → `/admin` не сработает.

### 6.2. Роль и база

```sql
CREATE ROLE logbook LOGIN PASSWORD '<пароль>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE DATABASE logbook OWNER logbook ENCODING 'UTF8' TEMPLATE template0;
\c logbook
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT ALL ON SCHEMA public TO logbook;
```

Требования к кластеру: UTF-8, `timezone = 'UTC'`, `password_encryption = scram-sha-256`. Приложение работает от одной роли; суперпользователь нужен только для `pg_dumpall --globals-only` и обслуживания.

### 6.3. TLS

`postgresql.conf`:

```conf
ssl = on
ssl_cert_file = '/etc/postgresql/15/main/server.crt'
ssl_key_file  = '/etc/postgresql/15/main/server.key'
ssl_min_protocol_version = 'TLSv1.2'
listen_addresses = '10.0.0.10'   # только сеть приложения
```

`pg_hba.conf` (порядок важен):

```
hostssl all         all         10.0.0.0/8  scram-sha-256
hostssl replication replicator  10.0.0.0/8  scram-sha-256
hostnossl all       all         0.0.0.0/0   reject
```

Проверка без TLS должна завершаться отказом:

```bash
psql "host=db.internal user=logbook dbname=logbook sslmode=disable" -c 'select 1'
# FATAL: no pg_hba.conf entry ... no encryption
psql "host=db.internal user=logbook dbname=logbook sslmode=verify-full sslrootcert=/etc/logbook/db-ca.pem" -c 'select 1'
```

`require` шифрует без проверки CA — допустим только в лаборатории. Подробно — [db/postgres/README.md](db/postgres/README.md).

```bash
# вариант 1: CLI (нужны dev-зависимости — tsx)

# вариант 3: на сервере только production-зависимости
#   сборка выполняется на build-хосте/CI, на сервер копируются dist, assets и node_modules
npm ci --omit=dev            # tsx недоступен
RUN_MIGRATIONS_ON_START=true node apps/api/dist/main.js   # миграции применит API
```

Правила:

- миграции только вперёд; откат — восстановление из backup (§13) или отдельная новая миграция;
- при нескольких инстансах API миграции должен применять **только один** процесс (отдельный job/инстанс); остальным — `RUN_MIGRATIONS_ON_START=false`, иначе возможна гонка;
- перед выпуском — backup и `POST /v1/admin/backup/checkpoint` (§13);
- проверка применённого набора: `SELECT count(*) FROM schema_migrations;` — на 27.11.2026 ожидается **17**.
- **обязательно после миграций/seed/bootstrap:** `npm run db:analyze` (или `ANALYZE;` в psql).
  Без статистики первый `/sync/changes` на холодной БД может выбрать seq scan:
  замер t30 — changes p95 612.1 мс при пороге 500, push 419.1 при пороге 400;
  после `ANALYZE` — 139.2/350.1 мс (см. `docs/loadtest/t30/README.md`).
  `npm run db:seed` уже выполняет `ANALYZE` в конце; `db:analyze` нужен, если
  seed не запускался (production bootstrap).
- **после bulk/scale/import/восстановления или длительного push-потока — обязательно повторить `ANALYZE`**.
  `db:seed` обновляет статистику только для seed-данных; scale fixture, CSV/JSON-импорт
  нарядов и накопленный push добавляют строки уже после него. Порядок для приёмки/нагрузки:
  ```bash
  npm run db:migrate
  npm run db:seed                    # ANALYZE для seed
  node scripts/pg/scale-fixture.mjs  # bulk: 5k users / 20k entries; ANALYZE в конце (t32)
  npm run db:analyze                 # обязательный повторный ANALYZE после fixture/import
  # только затем API и loadtest; loadtest.mjs тоже делает ANALYZE (LOADTEST_ANALYZE=1)
  # холодная приёмка: WARMUP_MS=60000 node scripts/pg/loadtest.mjs
  # (прогрев не измеряется, после него снова ANALYZE, затем 60 с измерения)
  ```
  t31: fresh 0001–0017 после seed-ANALYZE без повторного ANALYZE дал changes p95
  **798,7/1479,1 мс**; после `npm run db:analyze` — **139,9 мс** (push 354 мс).
  Без этого шага холодная приёмка/ production-трафик не считаются готовыми
  (F-01 residual, t32). Для воспроизведения «без ANALYZE» используйте
  `SCALE_SKIP_ANALYZE=1` и `LOADTEST_ANALYZE=0` — такие результаты не являются
  приёмочными.

## 7. TLS и reverse proxy

### 7.1. Схема TLS

| Участок | Решение |
|---|---|
| Браузер → nginx | TLS 1.2/1.3, сертификат корпоративного/публичного CA, HSTS |
| nginx → API | HTTP по `127.0.0.1:3001` (API TLS не реализует; порт не публикуется) |
| API → PostgreSQL | TLS `verify-full` + `DATABASE_SSL_CA_PATH` (§6.3) |
| OIDC API ↔ IdP | HTTPS обязателен (гейт `env.ts`) |

### 7.2. nginx: операционный origin

```nginx
limit_req_zone $binary_remote_addr zone=logbook_api:10m rate=20r/s;

server {
    listen 80;
    server_name logbook.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    # nginx >= 1.25.1: http2 on;
    server_name logbook.example.com;

    ssl_certificate     /etc/ssl/logbook/fullchain.pem;
    ssl_certificate_key /etc/ssl/logbook/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    root  /opt/logbook/current/apps/web/dist;
    index index.html;
    client_max_body_size 4m;

    # service worker и точка входа не кэшируются
    location = /service-worker.js { add_header Cache-Control "no-store" always; }
    location = /index.html       { add_header Cache-Control "no-store" always; }
    location = /manifest.webmanifest { add_header Cache-Control "no-cache" always; }
    location /assets/ { add_header Cache-Control "public, max-age=31536000, immutable"; }

    location /v1/ {
        limit_req zone=logbook_api burst=40 nodelay;
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }

    location / { try_files $uri $uri/ /index.html; }
}
```

Admin-origin — отдельный `server` с тем же `/v1`-прокси, но своим `root` (admin-сборка):

```nginx
server {
    listen 443 ssl;
    server_name admin.logbook.example.com;
    # ... TLS/HSTS аналогично ...
    root /opt/logbook-admin/web;   # сборка с VITE_ADMIN_ORIGIN=https://admin.logbook.example.com
    location = /service-worker.js { add_header Cache-Control "no-store" always; }
    location /v1/ {
        proxy_pass http://127.0.0.1:3001;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
    location / { try_files $uri $uri/ /index.html; }
}
```

> ⚠ В nginx `add_header` в `location` отменяет наследование серверных `add_header`: если задаёте `Cache-Control` в location, повторите там security-заголовки (или вынесите их в `include security-headers.conf;` и подключайте в каждом location). Иначе HSTS/`X-Content-Type-Options` пропадут на `/assets/`, `/index.html`, `/service-worker.js`.

**Каноническая конфигурация репозитория (AUTH-05):** `deploy/nginx/nginx.conf` +
`deploy/nginx/security-headers.conf` + `deploy/nginx/spa-csp.conf`. Она содержит
оба origin, HSTS, CSP SPA, `limit_req` для auth/API, no-store для SW/index,
`server_tokens off` и `http2 on`. Синтаксис проверяется исполняемо:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/security/verify-nginx.ps1
# nginx 1.28.0: "configuration file ... test is successful", NGINX CONFIG OK
```

Скрипт скачивает nginx для Windows, подставляет локальные пути/сертификат и
выполняет `nginx -t`; production-пути остаются `/etc/nginx/certs` и
`/var/www/logbook`.

Почему так: каждая SPA ходит в `/v1` своего origin, cookie host-only и у админки
отдельная сессия (ADR-14); `CORS_ORIGIN`/`ADMIN_ORIGIN` при этом остаются в
конфигурации API для валидации и на случай вызова API с другого origin.

Прочие замечания:

- Security headers реализованы на двух уровнях: API (`apps/api/src/common/security-headers.ts`:
  `nosniff`, `DENY`, `no-referrer`, `Permissions-Policy`, строгий CSP API, `no-store`;
  HSTS только в production) и nginx для SPA (CSP `deploy/nginx/spa-csp.conf`).
- Rate limit: API (`RATE_LIMIT_*`/`AUTH_RATE_LIMIT_*`, ответ `429 E-RATE-01` +
  `Retry-After`) плюс `limit_req` nginx для всех инстансов. Per-instance лимитер
  не заменяет edge-лимит при горизонтальном масштабировании.
- Idle timeout: `SESSION_IDLE_MINUTES` (по умолчанию 30, production ≤ 120);
  неактивная сессия отзывается сервером (`sessions.revoked_at`), следующий запрос — `401`.
- SCA: `npm audit` — 0 high/critical; 3 moderate остаются только в dev/build-цепочке
  Workbox (`glob`, `minimatch`, `workbox-build`), не попадают в production-образ
  (`npm ci --omit=dev`). Waiver и компенсации — `docs/security/SCA_WAIVER.md`.
- `try_files ... /index.html` обязателен: маршруты SPA (`/entries/:id`, `/admin/*`, `/journal/print`) не существуют как файлы.
- Сертификаты: `certbot renew --deploy-hook "systemctl reload nginx"` (или корпоративный CA); следите за сроком (§14).
- IIS: эквивалент — URL Rewrite (SPA fallback) + ARR (reverse proxy `/v1`), те же заголовки кэша для `service-worker.js`/`index.html`.

## 12. Обновление

### 12.1. Процедура

1. Прочитайте примечания к выпуску; проверьте новые миграции (`db/migrations`) и изменения `VITE_*`/env.
2. Сделайте backup и checkpoint:

```bash
# checkpoint в аудит (admin-сессия)
curl -b cookies.txt -X POST https://logbook.example.com/v1/admin/backup/checkpoint \
  -H 'Content-Type: application/json' -H "X-CSRF-Token: $CSRF" -d '{"label":"pre-upgrade-<версия>"}'
# логический backup
pg_dump -Fc -Z6 -f /var/backups/logbook/pre-upgrade-$(date +%F).dump "$DATABASE_URL"
```

3. Проверьте backup (см. §13.4) — обновление без проверенной копии не начинайте.
4. Разверните новый код в отдельный каталог (`/opt/logbook/releases/<версия>`), выполните `npm ci && npm run build`.
5. Остановите API, примените миграции (или стартуйте с `RUN_MIGRATIONS_ON_START=true`), запустите новую версию:

```bash
sudo systemctl stop logbook-api
cd /opt/logbook/releases/<версия>
sudo -u logbook env ENV_FILE=/etc/logbook/logbook.env npm run db:migrate
sudo ln -sfn /opt/logbook/releases/<версия> /opt/logbook/current
sudo systemctl start logbook-api
curl -fsS http://127.0.0.1:3001/v1/health
```

6. Опубликуйте новый `apps/web/dist` (atomic: новый каталог + смена симлинка `root` nginx), перезагрузите nginx; если используется отдельная admin-сборка — пересоберите её с `VITE_ADMIN_ORIGIN` и опубликуйте отдельно.
7. Проверьте: health, `audit/verify`, вход, лента, создание записи, синхронизация, PDF, админка, `schema_migrations`.
8. Сообщите пользователям о необходимости перезагрузить вкладку (service worker обновляется автоматически, но старый бандл может жить до перезагрузки).
9. Оставьте предыдущий релиз для отката кода.

### 12.2. Политика совместимости

- миграции — только аддитивные в пределах одного релиза; удаление/переименование колонок — отдельным релизом после остановки старой версии;
- старая версия API должна работать на новой схеме в течение окна обновления (rolling);
- при нескольких инстансах: сначала миграции одним job, затем последовательный перезапуск инстансов;
- `VITE_*` не обновляются на сервере — только новой сборкой web.

### 12.3. Откат

| Ситуация | Действие |
|---|---|
| Ошибка в новом коде, схема совместима | вернуть предыдущий релиз (симлинк/образ), перезапустить API, проверить health |
| Ошибка в миграции/данных | остановить API, восстановить pre-upgrade backup (§13.4), вернуть предыдущий релиз |
| Ошибка в web/кешировании | вернуть предыдущий `dist`, очистить кеш у пользователей (§15) |

Не редактируйте применённые SQL-файлы: checksum в `schema_migrations` заблокирует следующий запуск.

## 13. Резервное копирование и восстановление

### 13.1. Цели

| Параметр | Значение | Подтверждение |
|---|---|---|
| RPO | ≤ 1 мин при непрерывном WAL-архиве (`archive_timeout=60s`); ≤ 24 ч при только логических бэкапах | отчёт 29 |
| RTO | ≤ 4 ч (логическое восстановление 48 тыс. записей — секунды; запас на инфраструктуру) | отчёт 29 |
| Хранение бэкапов | 30 дней (ADM-06) | `backup.ps1 -KeepDays 30` |
| Проверка восстановления | ежеквартально + перед каждым обновлением | этот документ |

### 13.2. Ежедневный логический бэкап

Linux (production):

```bash
STAMP=$(date +%F)
pg_dump -Fc -Z6 -f /var/backups/logbook/logbook-$STAMP.dump "$DATABASE_URL"
pg_dumpall --globals-only -f /var/backups/logbook/globals-$STAMP.sql
sha256sum /var/backups/logbook/*-$STAMP.* > /var/backups/logbook/SHA256SUMS-$STAMP
find /var/backups/logbook -type f -mtime +30 -delete
```

Windows (лаборатория, параметры production передаются явно):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/pg/backup.ps1 `
  -DbHost db.internal -Port 5432 -User logbook -Password '<пароль>' `
  -Database logbook -OutDir D:\backups\logbook -KeepDays 30 `
  -SslMode verify-full -SslRootCert C:\logbook\certs\db-ca.pem
```

`backup.ps1` делает `pg_dump -Fc -Z6`, `pg_dumpall --globals-only`, SHA-256 на каждый файл, JSON-манифест (БД, размер, длительность, sslmode) и retention. В backup входят WORM-экспорты (`export_jobs.file_bytes`/`csv_bytes` — bytea), поэтому дамп растёт вместе с архивом.

Дополнительно перед бэкапом: `GET /v1/admin/backup/manifest` и `POST /v1/admin/backup/checkpoint` (фиксирует счётчики таблиц, головы аудита и хэши экспортов в аудите) — по ним сверяется восстановление.

Расписание:

```ini
# /etc/systemd/system/logbook-backup.service + .timer
[Service]
Type=oneshot
User=logbook
EnvironmentFile=/etc/logbook/logbook.env
ExecStart=/usr/local/bin/logbook-backup.sh
```

```ini
[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
```

`/usr/local/bin/logbook-backup.sh` — обёртка с командами из начала §13.2 и проверкой результата:

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F)
pg_dump -Fc -Z6 -f "/var/backups/logbook/logbook-$STAMP.dump" "$DATABASE_URL"
pg_dumpall --globals-only -f "/var/backups/logbook/globals-$STAMP.sql"
( cd /var/backups/logbook && sha256sum ./*-"$STAMP".* > "SHA256SUMS-$STAMP" )
test -s "/var/backups/logbook/logbook-$STAMP.dump"
find /var/backups/logbook -type f -mtime +30 -delete
```

Windows: планировщик задач, ежедневно 02:30, действие — `powershell -File scripts/pg/backup.ps1 ...`.

Копии — off-site (другой узел/хранилище) с шифрованием; доступ к каталогу бэкапов — только эксплуатации.

### 13.3. WAL и PITR

- `archive_mode=on`, `archive_command` копирует WAL в отдельный том/каталог (§6.4);
- базовая копия: `pg_basebackup -D /var/backups/logbook/base -X stream -c fast`;
- восстановление на точку: `recovery_target_time`, `restore_command`, `recovery_target_action='promote'` (лабораторный дрилл — `scripts/pg/pitr-drill.ps1`);
- проверка после PITR: маркер, записанный после целевой точки, отсутствует; таймлайн повышен; API стартует и `audit/verify` зелёный.

### 13.4. Восстановление и проверка

```bash
# 1) пустая БД
createdb -O logbook logbook_restore
# 2) восстановление
pg_restore -d logbook_restore -j 4 --exit-on-error /var/backups/logbook/logbook-2026-11-25.dump
# 3) сверка
psql -d logbook_restore -c 'ANALYZE'
psql -d logbook_restore -tAc 'select count(*) from schema_migrations'      -- 13
psql -d logbook_restore -tAc 'select count(*) from journal_entries'
psql -d logbook_restore -tAc 'select count(*) from audit_events'
```

Windows: `scripts/pg/restore.ps1 -Dump <файл> -TargetDatabase logbook_restore -SslMode verify-full -SslRootCert <CA>`; скрипт проверяет счётчики, число миграций (≥ 11) и согласованность `journal_counters` (должно быть 0 расхождений).

Полная проверка приложения на восстановленной копии:

1. переключить тестовый инстанс API на `logbook_restore` (`DATABASE_URL`);
2. `GET /v1/health` → `db=ok`;
3. вход администратором и `GET /v1/admin/audit/verify` → `ok=true`;
4. `GET /v1/admin/backup/manifest` и сравнение счётчиков с checkpoint, сделанным до бэкапа;
5. выборочно открыть 2–3 записи и PDF наряда.

Сверка счётчиков с манифестом — обязательный шаг: успешный `pg_restore` без сверки не доказывает полноту данных.

### 13.5. HA и failover

`docker compose --profile ha up -d` поднимает streaming-реплику (`pg_basebackup -X stream -R`). Проверка:

```sql
-- primary
select client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) as lag_bytes
  from pg_stat_replication;
-- replica
select pg_is_in_recovery(), pg_last_wal_replay_lsn();
```

Promotion (только по runbook, при отказе primary):

1. остановить API;
2. `pg_ctl promote` на реплике (или управляемый failover);
3. переключить `DATABASE_URL` на новый primary, перезапустить API;
4. проверить `health`, `audit/verify`, отсутствие записи на старом primary.

Лабораторный дрилл — `scripts/pg/replica-drill.ps1` (lag 0, promotion ~474 мс, запись после promotion). Автоматического failover нет (нужен Patroni/облачный сервис) — открытый пункт.

Логи API — stdout (journald/файл); формат NestJS. Метрик `/metrics` нет (⚠ ADM-05): используйте health-проверку, `pg_stat_*` и журнал аудита; при необходимости добавьте экспортёр перед API.

**Loadtest (QA-06, F-01/F-02).** Перед измерением: свежая БД → `db:migrate` →
`db:seed` (включает ANALYZE) или `db:analyze`. API запускается с
`LOADTEST_RATE_LIMIT_DISABLED=true` (только вне production; `env.ts` отклонит
это в production) и `DATABASE_POOL_MAX=28`; затем
`BASE_URL=... DURATION_MS=60000 CONCURRENCY=20 RAMP_MS=3000 WARMUP_MS=60000 MIX=read:50,changes:15,push:30,snapshot:5 node scripts/pg/loadtest.mjs`.
`WARMUP_MS` создаёт нагрузку без учёта в метриках, после чего harness повторяет
`ANALYZE`; без этого cold-замер после bulk/scale недостоверен (t32).
Production-лимиты проверяются отдельным коротким прогоном с
`LOADTEST_RATE_LIMIT_DISABLED=false`, `RATE_LIMIT_MAX=300`; ожидаемо 429/E-RATE-01,
его error rate **не** является performance-порогом. Точные команды, JSON и

## 15. Диагностика

| Симптом | Причина | Действие |
|---|---|---|
| `Invalid environment configuration: ...` | env не проходит fail-closed | исправить поле из сообщения (§5.6); не отключать гейт |
| API не стартует: `ECONNREFUSED`/`ETIMEDOUT` к БД | неверный `DATABASE_URL`, сеть, кластер остановлен | `pg_isready`, firewall, `systemctl status postgresql` |
| `self-signed certificate in certificate chain` | CA не совпадает / нет `DATABASE_SSL_CA_PATH` | положить корневой CA, `verify-full`, проверить `sslrootcert` через `psql` |
| `no pg_hba.conf entry ... no encryption` | клиент без TLS, `hostssl`-only | включить `DATABASE_SSL_MODE=require/verify-full`; не ослаблять `pg_hba` |
| `password authentication failed` | пароль/`scram-sha-256` | `ALTER ROLE logbook PASSWORD ...`, `password_encryption=scram-sha-256` |
| `Migration 0001_init.sql was modified after being applied` | изменён применённый файл | вернуть исходный файл; изменения — только новой миграцией |
| `Migration 00xx ... failed` | ошибка SQL/несовместимая схема | восстановить backup, исправить миграцию в новом файле, повторить |
| `EADDRINUSE :::3001` | порт занят (второй инстанс/dev-сервер) | остановить лишний процесс или сменить `PORT` |
| `remaining connection slots are reserved` | пул × инстансы > `max_connections` | уменьшить `DATABASE_POOL_MAX`/число инстансов, поднять `max_connections` |
| После входа снова `/login` по HTTP | `NODE_ENV=production` → cookie `Secure` не сохраняется по http | использовать https (production) или `NODE_ENV=development` в лаборатории |
| `403 CSRF-токен отсутствует или не совпадает` | мутация без `X-CSRF-Token` | передавать cookie `lb_csrf` в заголовке; для admin-origin — токен из `GET /v1/me.csrf_token` |
| `403` при sync/push | устройство отозвано/нет `X-Device-Key` | перерегистрировать устройство (`POST /v1/devices`), передать ключ |
| `/login?auth_error=...` | истёк state (10 мин), неверный redirect URI, пользователь не создан, email не подтверждён, IdP недоступен | сверить `OIDC_REDIRECT_URI` с IdP, проверить discovery/JWKS, создать пользователя, `email_verified` |
| CORS-ошибка в админке | `ADMIN_ORIGIN` не задан/не совпадает с `VITE_ADMIN_ORIGIN` | задать оба, пересобрать admin-бандл, перезапустить API |
| 404 при обновлении страницы SPA | нет fallback на `index.html` | добавить `try_files $uri $uri/ /index.html` |
| После обновления старый интерфейс | кеш service worker | жёсткая перезагрузка; проверить `Cache-Control: no-store` для `service-worker.js`/`index.html`; при необходимости «Unregister» SW |
| PDF наряда `500` | нет `apps/api/assets/OpenSans-Regular.ttf` рядом с `dist` | скопировать `assets` в выпуск |
| Скачивание экспорта `403` | истёк/подменён signed URL (> 900 с) | запросить новую ссылку `POST /v1/exports/{id}/url` |
| `audit/verify` → `broken` | подмена/частичное восстановление | остановить запись, восстановить из backup, разобрать `audit_events`, эскалация ИБ |
| Restore: расхождение `journal_counters` | частичный restore, ошибки `pg_restore` | повторить с `--exit-on-error`, сверить `schema_migrations` и counts |
| Заполнен диск / PostgreSQL остановился | не работает `archive_command`, WAL копится | `pg_stat_archiver.failed_count`, починить архив, освободить место, проверить `archive_timeout` |
| Push 50 операций медленный (p95 > 400 мс) | известный дефект: транзакция на операцию + сериализация `journal_counters` (QA-06) | проверьте, что выпуск содержит `0013` и батчевый push (t17); до этого — ограничить размер батча и мониторить блокировки |
| `npm test`/`typecheck` падает на старом Node | Node < 22, PGlite WASM/ESM | установить Node ≥ 22 |
| PowerShell блокирует скрипты | ExecutionPolicy | `powershell -NoProfile -ExecutionPolicy Bypass -File ...` |
| Два инстанса API на PGlite «ломают» данные | PGlite — локальный файл/память | production только PostgreSQL; PGlite — один процесс |
| `relation ... does not exist` после старта | миграции не применены | `npm run db:migrate` или `RUN_MIGRATIONS_ON_START=true` |

## 16. Вывод из эксплуатации

Данные ЭОЖ подлежат хранению по утверждённой политике (OQ-05/OQ-18, по умолчанию 3 года). Удаление БД не защищено retention-триггером — юридическое согласование обязательно.

1. **Архивирование (обязательно):** сформировать WORM PDF/CSV за весь период, скачать и проверить подписи/хэши; выгрузить аудит (`GET /v1/audit`), manifest/checkpoint; сохранить копии на носитель с контролем доступа.
2. Уведомить пользователей, перевести контур в режим только чтения (при необходимости).
3. Остановить и отключить службы: `systemctl disable --now logbook-api`, таймеры backup; в Windows — `nssm stop/remove` или `schtasks /Delete`.
4. Снять nginx-конфигурации, отозвать сертификаты, закрыть 443.
5. Удалить БД и WAL-архив: `dropdb logbook`, удалить каталог WAL; в Docker — `docker compose --profile ha down -v`.
6. Удалить приложение и данные: `/opt/logbook` (включая `.data`, если использовался PGlite), `node_modules`, локальные бэкапы (после истечения срока).
7. Отозвать `OIDC_CLIENT_ID` у IdP, ротировать/удалить секреты (`COOKIE_SECRET`, `SIGNATURE_SECRET`, `PERMIT_PDF_SECRET`, `EXPORT_SIGNING_SECRET`, пароль БД).
8. Удалить DNS-записи и служебную учётную запись `logbook`.
9. Клиенты: удалить PWA/данные сайта (Chrome → Settings → Site data → logbook.example.com; это удаляет IndexedDB с офлайн-очередью — предупредить пользователей).
10. Оформить акт уничтожения: дата, состав данных, кто выполнил, где архив, срок хранения архива.

Проверка после удаления: порты 3001/5432/443 закрыты, БД отсутствует, секреты отозваны, остались только архивные копии по политике.
