# Модель данных ЭОЖ «Logbook»

| Параметр | Значение |
|---|---|
| Версия | 2.5 |
| Дата | 25.11.2026 |
| СУБД | PostgreSQL 15+ (сервер), IndexedDB (клиент) |
| Изменения относительно v2.4 | Батчевый push (t17): `journal_seq` выдаётся блоками из per-journal sequence `journal_seq_<uuid>` (`0014`), триггер не трогает `journal_counters` для явного номера (`0013`); `journal_counters` — legacy/fallback |

---

## 1. Принципы

1. Идентификаторы клиентских сущностей — UUID v7, генерируются на устройстве.
2. Два времени: клиентское (`*_client`) и серверное (`*_server`); бизнес-время (`performed_at`) — отдельно.
3. Мягкое удаление (`deleted_at`, tombstone) для записей, нарядов и пользователей; физическое удаление запрещено.
4. Версионирование: `version` (монотонно, сервер) + `hlc` (порядок, клиент) + `field_clocks` (полевой merge).
5. Справочники нормализованы; в записях — только ссылки.
6. Клиент хранит минимально необходимое; сервер — полную историю.
7. Все изменения сущностей, участвующих в синхронизации, попадают в `change_log` с монотонным `seq`.

## 2. Связи

```
Department 1──N User
User       1──N JournalEntry (author)
User       1──N Device
User       N──M Permit          (через PermitParticipant)
User       N──M Journal         (через JournalMember)
Journal    1──N JournalEntry
Journal    1──N JournalReview
Journal    1──N Shift
Journal    1──N Grounding
User       1──N Shift           (handed_over_by / accepted_by)
User       1──N Grounding       (applied_by / removed_by)
Journal    1──1 JournalCounter  (номер последней записи)
WorkType   1──N JournalEntry
WorkType   1──N Template
Site       1──N JournalEntry
Site       1──N Permit
Site       1──N Site             (parent_id, иерархия ≤ 5)
Permit     1──N JournalEntry
JournalEntry 1──N EntryRevision
JournalEntry 1──N EntryWorker N──1 User
JournalEntry 1──N ConflictRecord
JournalEntry 1──N Attachment
OutboxOperation N──1 JournalEntry
ChangeLog      N──1 (полиморфная ссылка)
```

| Связь | Кардинальность | Удаление |
|---|---|---|
| `User → Department` | N:1 | Подразделение нельзя удалить при активных пользователях |
| `Journal → JournalEntry` | 1:N | Записи не удаляются; журнал деактивируется |
| `Journal → JournalReview` | 1:N | Визы хранятся вместе с журналом |
| `Journal → Shift` | 1:N | Смены хранятся вместе с журналом |
| `Journal → Grounding` | 1:N | Реестр заземлений журнала |
| `Grounding → JournalEntry` | N:1 | Строка реестра ссылается на события установки/снятия |
| `Shift → User` (handed_over_by / accepted_by) | N:1 | Пользователь деактивируется, смена сохраняется |
| `Journal → JournalMember → User` | 1:N:M | Каскадно при удалении журнала/пользователя |
| `JournalEntry → User` | N:1 | Пользователь деактивируется, записи сохраняются |
| `JournalEntry → Permit` | N:1, nullable | Наряд помечается `is_deleted`, ссылка сохраняется |
| `JournalEntry → WorkType/Site` | N:1 | Архивирование, не удаление |
| `JournalEntry → EntryRevision` | 1:N | Ревизии не удаляются |
| `JournalEntry → EntryWorker → User` | 1:N:M | Мягкое удаление вместе с записью |
| `Permit → PermitParticipant → User` | 1:N:M | Каскадное удаление участников при удалении наряда |
| `JournalEntry → ConflictRecord` | 1:N | Удаляются вместе с записью (мягко) |
| `JournalEntry → Attachment` | 1:N | Мягкое удаление; файл — по политике |
| `OutboxOperation → JournalEntry` | N:1 | Удаляются после `ack` |
| `AuditEvent → User` | N:1 | Не удаляются |

### 3.12. Journal, JournalMember, JournalCounter, JournalReview (мультижурнальность)

| Сущность | Поля | Правила |
|---|---|---|
| `Journal` | `id`, `journal_key` (2–64, `^[a-z0-9][a-z0-9_-]*$`, уникален), `name`, `description`, `active`, `sort_order`, `created_at` | `journal_key` неизменяем; деактивация вместо удаления; `main` — журнал по умолчанию |
| `JournalMember` | `journal_id`, `user_id`, `access_level` (`read` / `write` / `manage`), `granted_by`, `granted_at` | PK `(journal_id, user_id)`; `admin` имеет `manage` во всех журналах, `auditor` — `read` |
| `JournalCounter` | `journal_id` (PK/FK), `last_seq` (bigint ≥ 0), `updated_at` | Атомарное выделение номера через `INSERT … ON CONFLICT DO UPDATE … RETURNING` |
| `JournalReview` | `id`, `journal_id`, `journal_key`, `period_start`, `period_end`, `reviewer_id`, `reviewed_at`, `entries_count`, `remarks`, `content_hash` | Период в одном журнале; `content_hash` включает `journal_id`/`journal_key` и только записи этого журнала |

**Правила нумерации.** `journal_entries.journal_seq` не глобальный `bigserial`: для каждого журнала существует PostgreSQL sequence `journal_seq_<uuid>` (миграция `0014`). Батчевый push (`t17`) резервирует блок номеров одним `nextval(...) FROM generate_series(1,N)` и передаёт явный `journal_seq`; триггер `journal_entries_assign_seq` принимает явный номер без записи в `journal_counters` (`0013`), а при `NULL` берёт следующий из sequence. `journal_counters` остаётся legacy/fallback (backfill и журналы без sequence) и не обновляется на горячем пути. Две записи в разных журналах могут иметь одинаковый `journal_seq`; уникальность — `(journal_id, journal_seq)`. Sequence нетранзакционна: при полном откате батча возможны разрывы (допустимо, зафиксировать в правилах журнала).

**Права.** `worker`/`supervisor` видят журнал `main` без явного гранта (обратная совместимость); остальные журналы — только при наличии `journal_members` (`read` — чтение, `write` — создание записей и визы, `manage` — управление участниками). `admin` управляет всеми журналами, `auditor` читает все активные.

| `handed_over_at` | timestamptz | да | Серверное время сдачи |
| `handover_comment` | varchar(1000) | да | 5–1000 после trim |
| `accepted_by`, `accepted_at` | uuid, timestamptz | усл | Обязательны при `accepted`; `accepted_by <> handed_over_by` |
| `acceptance_comment` | varchar(1000) | нет | Замечания/отметка приёмки |
| `rejected_by`, `rejected_at` | uuid, timestamptz | усл | Обязательны при `rejected` |
| `rejection_reason` | varchar(500) | усл | Обязательна при `rejected` |
| `entries_count` | int | да | Снимок числа активных записей журнала за окно |
| `entries_hash` | char(64) | да | SHA-256 снимка записей (`id`, `version`, `hlc`, `journal_seq`) |
| `content_hash` | char(64) | да | Hash редакции для подписи (handover v1 / acceptance v2) |
| `version` | int | да | 1 — сдача, 2 — приёмка/отклонение |
| `hlc` | varchar(32) | да | HLC операции |
| `created_at_client/server`, `updated_at_client/server` | timestamptz | да | Два времени |
| `device_id`, `last_op_id` | uuid | нет | Устройство/операция последней записи |

**Правила:**
- Сдаёт и принимает смену только `supervisor`/`admin`; принимающий обязан быть другим пользователем (проверка БД и API). Свою смену принять нельзя.
- Активная смена одна на `(journal_id, shift_date, period_start)` (partial unique index для `handed_over`/`accepted`); после отклонения можно сдать заново.
- Обе стороны работают офлайн: сдача — `create` в outbox (`entity_type=shift`), приёмка/отклонение — `update` с `base_version`; сервер применяет по версии, при гонке возвращает конфликт с актуальным состоянием.
- Подписи: `document_signatures` с `entity_type='shift'`, `entity_version=1` — сдающий, `=2` — принимающий. Подпись сдачи не инвалидируется приёмкой: `shiftHandoverContentHash` не включает поля приёмки; `shiftAcceptanceContentHash` связывает решение с hash сдачи.
- Аудит: `shift.handover`, `shift.accept`, `shift.reject` + `signature.create`; `change_log` получает `entity_type='shift'` для синхронизации других устройств.

### 3.14. Grounding (реестр заземлений, JRN-06)

| Поле | Тип | Обяз | Ограничения / правило |
|---|---|---|---|
| `id` | uuid | да | PK |
| `journal_id` | uuid | да | FK `journals` |
| `site_id` | uuid | нет | FK `sites` (объект из события) |
| `point` | varchar(200) | да | Точка установки |
| `grounding_type` | enum | да | `portable` (переносное З/З) / `fixed` (ЗН) |
| `tool_number` | varchar(64) | нет | Номер средства защиты |
| `count` | int | да | 1–100 |
| `state` | enum | да | `applied` / `removed` |
| `applied_entry_id`, `applied_by`, `applied_at` | uuid, uuid, timestamptz | усл | Обязательны при `applied` |
| `removed_entry_id`, `removed_by`, `removed_at` | uuid, uuid, timestamptz | усл | Обязательны при `removed` |
| `version` | int | да | ≥ 1, растёт при снятии |
| `created_at_server`, `updated_at_server` | timestamptz | да | Серверные времена |

**Правила:**
- Строка реестра создаётся сервером из события `event_type='grounding'`: `action='applied'` — новая активная строка, `action='removed'` — закрытие активной.
- Активная строка одна на `(journal_id, site, point, grounding_type, tool_number)` (partial unique). Повторная установка или снятие не блокирует запись журнала, но возвращает `conflict` и создаёт `conflict_records.field='grounding_state'` для разбора.
- Событие заземления неизменяемо после создания: правка `event_type/event_data` отклоняется (`E-VAL-01`); для изменения состояния фиксируется новое событие.
- Аудит: `grounding.applied`, `grounding.removed`, `grounding.conflict`; `change_log` — `entity_type='grounding'`.
- История сохраняется: после снятия строка остаётся со `state='removed'`, повторная установка создаёт новую строку.

**Структурированные переключения (757).** `journal_entries.event_data` для `event_type='switching'`: `order_no`, `order_date`, `responsible`, `operations[]` (`operation: open|close|check|measure|other`, `device`, `from_state`, `to_state`, `note`), `checks[]` (`check`, `passed`, `note`), `executed_at`, `points`. Старый свободный `sequence` (строка) принимается для обратной совместимости. Валидация: неизвестная операция или пустой бланк (нет операций/устаревшей последовательности/оборудования) отклоняются.

### 3.15. Export, retention и архив (JRN-04/JRN-07)

| Сущность | Поля | Правила |
|---|---|---|
| `ExportJob` | см. §3.11; для PDF/CSV: `file_bytes`/`csv_bytes` (bytea), `file_sha256`/`csv_sha256`, `file_size_bytes`/`csv_size_bytes`, `manifest` jsonb, `signature_id`, `generated_at`, `worm`, `download_count` | `status='done'` неизменяем (триггер WORM), удаление запрещено; signed URL TTL ≤ 900 с; скачивание аудируется |
| `ArchiveManifest` | `id`, `export_job_id` (unique), `journal_id`, `period_from`, `period_to`, `entries_count`, `pdf_sha256`, `csv_sha256`, `manifest`, `created_at` | Создаётся при архивации записей старше retention-cutoff; UPDATE/DELETE запрещены |
| `RetentionRun` | `id`, `run_at`, `actor_id`, `policy_years`, `cutoff`, `audit_ok`, `streams_checked`, `report`, `created_at` | Ежедневная/ручная проверка: отчёт + проверка hash-цепочки аудита; неизменяем по смыслу |
| `BackupCheckpoint` | `id`, `created_at`, `actor_id`, `label`, `manifest`, `manifest_hash` | Хук перед backup: фиксирует manifest (счётчики таблиц, головы аудита, хэши экспортов) |

**Retention.** Политика — `RETENTION_YEARS` (по умолчанию 3; OQ-05/OQ-18 не утверждены). Записи журнала физически не удаляются до `performed_at + 3 года` (триггер `journal_entries_retention_guard`); мягкое удаление разрешено. Отчёт: `GET /v1/admin/retention`; проверка аудита: `GET /v1/admin/audit/verify`; запуск с отчётом: `POST /v1/admin/retention/run` (ускоренное время `now` для тестов). Архив: `POST /v1/admin/retention/archive` создаёт WORM export + `archive_manifests`; восстановление — скачивание архива по signed URL. Backup-хуки: `GET /v1/admin/backup/manifest` и `POST /v1/admin/backup/checkpoint` перед `scripts/pg/backup.ps1`.

**WORM-экспорт.** `POST /v1/journal/exports` (supervisor/admin/auditor) формирует серверный PDF 3-графной формы (дата/№, содержание, визы/замечания; `journal_seq` и статус подписи по записи) и CSV, manifest с SHA-256 обоих файлов; PDF подписывается ЭП-адаптером (`document_signatures.entity_type='export'`, content hash = SHA-256 файла), подпись проверяется `/signature/:id/verify` и остаётся валидной, пока файл неизменяем. Скачивание — по signed URL `/v1/exports/:id/download` (TTL ≤ 900 с), события `journal.export.pdf`, `export.url`, `export.download` в аудите.

### 4.2. Клиент (IndexedDB)

`entries`: `author_id+performed_at`, `permit_id`, `sync_status`, `status`, `journal_id`, `[journal_id+performed_at]`; `outbox`: `status+next_attempt_at`, `entity_id`; `permits`: `number_norm`, `status+valid_to`; `search_index`: `token`; `conflicts`: `entry_id`; `journals`: `journal_key`, `active`, `sort_order`; `journal_reviews`: `period_start`, `period_end`, `reviewer_id`, `journal_key`, `journal_id`; `shifts`: `journal_id`, `shift_date`, `status`, `handed_over_by`, `accepted_by`, `sync_status`; `groundings`: `journal_id`, `site_id`, `state`, `point`, `grounding_type`; `supervisor_cache`: `journal_id`, `user_id`, `updated_at`.

**Базы IndexedDB (SYN-02, ADR-16).** Данные разделены по владельцу:

| База | Содержимое | Жизненный цикл |
|---|---|---|
| `logbook:device` | `device_id`, `install_id`, `device_key:<id>`, `device_node`, `hlc_last`, `csrf_token` (для SW), `active_user_id`, `last_user_id`, `known_users`, `background_sync_status`, `sw_last_flush`, отчёты переноса | Не удаляется при выходе пользователя; сбрасывается только при отвязке устройства |
| `logbook:user:<user_id>` | записи, ревизии, `entry_workers`, наряды, справочники, журналы, визы, `shifts`, `groundings`, `outbox`, конфликты, черновики, `sync_state`, `supervisor_cache`, `meta` | Удаляется при выходе с очисткой (`logout`); при блокировке (`lock`) остаётся на диске |
| `logbook` (legacy) | Старая общая база | Одноразовый перенос строк входящего пользователя при первом входе; удаляется после полного переноса (после снимка) |

Кэш руководителя: `supervisor_cache` хранит окно 7 дней и объём по каждому журналу; записи кэшируются в общий `entries` пользователя и вытесняются по возрасту/бюджету (15 МиБ), не затрагивая свои записи и pending-операции.

**Миграции Dexie v2 → v3 → v4 → v5.** Старые локальные записи и визы получают `journal_id = main` в одной транзакции upgrade; данные не теряются, фильтр по журналу сразу доступен офлайн. Каталог журналов приходит в снапшоте справочников (`journals`) и кэшируется; до первого снапшота используется встроенный `main`. v4 добавляет per-user БД, store `shifts`, `supervisor_cache` и составной индекс `journal_id+performed_at`; существующие строки нормализуются (`journal_id`, `sync_status`). v5 добавляет `groundings` — кэш реестра заземлений для офлайн-экрана. Перед апгрейдом (ADR-18) снимается снимок всех stores в `logbook:...#snapshot:<ts>`, после апгрейда проверяются счётчики, при ошибке данные восстанавливаются из снимка (см. `27_Отчёт_Offline_Platform.md`).

## 5. Ограничения и правила целостности

| ID | Правило |
|---|---|
| DC-01 | `author_id` записи неизменяем |
| DC-02 | `performed_at` не может быть позже `now + 5 мин` (серверное время) |
| DC-03 | `text` — 10–2000 символов после trim; без управляющих символов, кроме `\n` |
| DC-04 | `permit_id` и `permit_number_raw` не могут быть заданы одновременно при `linked` |
| DC-05 | `permit_binding_status = linked` требует `permit_id` |
| DC-06 | `input_method = voice` требует `asr_engine` |
| DC-07 | `revision_no` уникален в пределах записи |
| DC-08 | `version` увеличивается только сервером |
| DC-09 | `op_id` уникален; повтор возвращает сохранённый ответ |
| DC-10 | `change_log.seq` строго возрастает |
| DC-11 | `audit` — только вставка; `prev_hash` ссылается на предыдущую запись потока по `stream_seq` |
| DC-12 | `permit` уникален по `(source_id, year, number_norm)` |
| DC-13 | `EntryWorker` — не более 20, все пользователи активны |
| DC-14 | `Attachment` — не более 5 на запись, ≤ 5 МБ каждое, ≤ 20 МБ суммарно |
| DC-15 | `permit_risk_flag = true` требует непустой `permit_risk_reason` |
| DC-16 | `journal_entries.journal_id` неизменяем: смена журнала запрещена триггером и API |
| DC-17 | `journal_seq` уникален в пределах журнала; выдаётся сервером и никогда не переиспользуется |
| DC-18 | Запись создаётся только в журнале, где у пользователя `write`/`manage`; без `journal_id` — в `main` |
| DC-19 | Виза (`JournalReview`) считается по записям одного журнала; её `content_hash` включает `journal_id` |
| DC-20 | `Shift.handed_over_by <> Shift.accepted_by`; сдающий не может принять свою смену |
| DC-21 | Активная смена одна на `(journal_id, shift_date, period_start)`; после `rejected` разрешена повторная сдача |
| DC-22 | `Shift.status='accepted'` требует `accepted_by/accepted_at`; `rejected` — `rejected_by/rejected_at/rejection_reason` |
| DC-23 | `entries_count`/`entries_hash` фиксируются при сдаче и не меняются при приёмке |
| DC-24 | `content_hash` сдачи не зависит от полей приёмки; подпись сдачи остаётся действительной после приёмки |
| DC-25 | Активная строка `groundings` одна на журнал/объект/точку/тип/номер; повторная установка или снятие → конфликт `grounding_state` |
| DC-26 | Событие `grounding` неизменяемо после создания; состояние меняется только новым событием |
| DC-27 | `switching.event_data` содержит операции с допустимым `operation`; пустой бланк отклоняется |
| DC-28 | Запись журнала физически не удаляется, пока `performed_at` моложе retention-cutoff (3 года); мягкое удаление разрешено |
| DC-29 | Завершённый экспорт (`status='done'`) и `archive_manifests` неизменяемы и не удаляются (WORM-триггеры) |
| DC-30 | Signed URL экспорта привязан к id/формату/SHA-256 файла и истекает ≤ 15 мин |

## 7. Совместимость и миграции

1. **Клиент (IndexedDB):** версия схемы в `meta`; миграция — в одной транзакции; перед миграцией — снимок всех store в отдельную базу `logbook:...#snapshot:<ts>`; после апгрейда — проверка счётчиков, при ошибке — восстановление из снимка и сообщение (ADR-18). Текущая версия — **v5** (`journals`, `journal_id`, `shifts`, `groundings`, `supervisor_cache`, per-user БД), upgrade добавляет `main` старым записям.
2. **Сервер:** только обратно-совместимые миграции (add column → backfill → switch → drop); окно поддержки — 2 версии API. Мультижурнальность — `0008_multi_journal.sql`, смены — `0009_shifts.sql`, реестр заземлений — `0010_groundings.sql`, PDF наряда — `0011_permit_pdf.sql`, retention/WORM-экспорт — `0012_retention_export.sql`, батчевый push/sequence — `0013_batch_journal_seq.sql`/`0014_journal_sequences.sql` (после `0007_auth_platform.sql`).
3. **Клиент-сервер:** сервер принимает поля, которых нет в старой версии, игнорируя их; новые обязательные поля вводятся с дефолтом.
4. **Проверка:** миграция тестируется на базе 10 000 записей и 10 000 операций очереди.
