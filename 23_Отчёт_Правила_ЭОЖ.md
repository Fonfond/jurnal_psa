## 1. Что применяем, адаптируем и не переносим

| Правило | Решение |
|---|---|
| Хронология, события, команды, работы, допуски, смена | **Применяем** как содержание журнала |
| 3 графы: дата/время, содержание, визы/замечания | **Адаптируем**: поля и печатная 3-графная форма |
| Сдача/приёмка смены, подписи, схема, инструмент, СИЗ, заземления, ключи | **Отложено**: нужна двухсторонняя приёмка/подпись и отдельная сущность |
| Визы не реже 2 раз в месяц | **Реализовано**: `journal_reviews`, не блокирует записи |
| Хранение 3 года | **Политика + экспорт**; автоудаление отложено (`TODO(OQ-18)`) |
| Сквозная нумерация | **Реализовано**: `journal_seq bigserial` + уникальный индекс |
| Исправления без подчисток | **Реализовано**: ревизии/audit/HLC |
| «Пропущенная запись» | **Реализовано**: `late_entry`, различие времени события и фиксации |
| Сокращения | **Реализовано** как справочник-подсказка без автозамены |
| Цвет пасты, «зигзаг», поля, прошнурование, печать | **Не переносим** буквально; эквивалент — нумерация, hash-аудит и контролируемая печать |
| Электронная подпись | **Не реализована**; 894 требует ЭП для журнала без бумаги. `TODO(OQ-04)` |

**Принципиально:** текущий hash-аудит и cookie-сессия **не являются электронной подписью**. До юридического решения Logbook остаётся гибридным: электронный журнал + печатная/подписанная копия.

## 2. Принятые решения

1. **Журнальный слой, а не полная замена бумажного журнала.** Пилот — гибридный режим; юридическая замена только после OQ-04.
2. **Аддитивная миграция.** Новые поля не ломают старые payload'ы; `event_type` по умолчанию `work`.
3. **`journal_seq` — глобальный для одного журнала.** Мультижурнальность требует `journal_id` и отдельного решения.
4. **Визы — контроль, не блокировка.** Отсутствие визы не запрещает запись, но отображается.
5. **Смена не имитируется.** Двухсторонняя приёмка/подпись — отдельная итерация, иначе создаётся ложное соответствие.
6. **ЭП не подменяется аудитом.** Экспорт и печать явно помечены «не подписано ЭП».

## 3. Реализация

### 3.1. Shared

- `JournalEventType`: `work`, `command`, `switching`, `grounding`, `incident`, `other`.
- `JournalEventData`: команда, переключение, заземление (`З/З` / `ЗН`), инцидент, другое.
- `JournalEntry`: `event_type`, `event_data`, `journal_seq`, `late_entry`.
- `JournalReview`.
- Zod-схемы `eventDataSchemas`, `journalReviewCreateSchema`, `validateEventData`.
- `abbreviations.ts` — справочник приложения 2 (без автозамены).

### 3.2. Миграция `0006_operational_journal.sql`

Аддитивно:

- `journal_entries.event_type journal_event_type_enum NOT NULL DEFAULT 'work'`;
- `event_data jsonb`;
- `journal_seq bigserial` + уникальный индекс;
- `late_entry boolean NOT NULL DEFAULT false`;
- таблица `journal_reviews` с периодом, проверяющим, количеством записей, замечаниями и `content_hash`.

Миграция проверена на существующей PGlite-базе: `0006` применилась поверх 0005 без потери данных.

### 3.3. API `/v1`

- Push/entries принимают `event_type`, `event_data`, `late_entry`; старые payload'ы получают `work`.
- `journal_seq` назначает сервер; клиент его не отправляет.
- `GET /v1/journal/reviews`, `POST /v1/journal/reviews` — supervisor/admin, аудит, hash содержимого.
- `GET /v1/journal/export?from&to&format=csv` — CSV с 3-графной логикой, `journal_seq`, видимостью по роли, пометкой об ЭП и хранении.
- C-10 валидация учитывает `event_data`.

### 3.4. Web

- Dexie `version(2)`, store `journal_reviews`; новые поля записи.
- S-02: тип события, `journal_seq`, «Пропущенная запись», печать/CSV.
- S-03: тип события, структурированные поля команды/переключения/заземления/инцидента, `late_entry`, подсказки сокращений.
- S-05: номер, тип, event_data.
- S-14 `/journal/reviews`: создание и история виз.
- `/journal/print`: 3-графная печатная форма, подпись ответственного, предупреждение об ЭП и хранении.
- Nav: добавлен пункт «Визы».
