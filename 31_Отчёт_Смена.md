## 1. Модель

`shifts`: `id`, `journal_id`, `shift_date`, окно `period_start/period_end`, `status`
(`handed_over` / `accepted` / `rejected` / `cancelled`), стороны `handed_over_by/at` и
`accepted_by/at` (или `rejected_by/at/reason`), комментарии, снимок смены
`entries_count`/`entries_hash` (активные записи журнала за окно), `content_hash`,
`version`, `hlc`, клиентские/серверные времена, устройство и операция. Ограничения:
`period_start < period_end`, комментарий 5–1000, обязательные поля приёмки/отклонения,
`accepted_by <> handed_over_by`, partial unique index — одна активная смена на
`(journal_id, shift_date, period_start)`.

`signature_entity_type_enum` расширен значением `shift`. Подписи хранятся в
`document_signatures`: `entity_version=1` — сдающий (handover hash), `=2` — принимающий
(acceptance hash, включающий hash сдачи). Подпись сдачи не инвалидируется приёмкой.

## 2. API

- `GET /v1/shifts?journal_id&status&from&to&limit` — supervisor: доступные журналы;
  worker: только свои сдачи/приёмки; admin/auditor: все.
- `GET /v1/shifts/{id}` — смена + `signatures[]`.
- `POST /v1/shifts` — сдача (supervisor/admin, доступ `write` к журналу), 201.
- `POST /v1/shifts/{id}/accept` — приёмка другим пользователем, 201.
- `POST /v1/shifts/{id}/reject` — отклонение с причиной, 201.

Ошибки: своя смена — 403; повторная приёмка/отклонение — 409; дубль активной смены —
409; нет доступа к журналу — 403; неверное окно/комментарий — 400. Каждое действие
пишется в `audit_events` (`shift.handover/accept/reject`) и `change_log`
(`entity_type='shift'`).

## 3. Офлайн и синхронизация

`sync/push` принимает `entity_type='shift'`: `create` — сдача, `update` — приёмка или
отклонение с `base_version`. Сервер проверяет права, версию и статус; при гонке
возвращает `status=conflict` и `merged_shift` с актуальным состоянием. Идемпотентность —
по `op_id` (общий `idempotency_records`). `sync/changes` отдаёт смены по тем же правам,
что и список. Клиент: Dexie v4 store `shifts`, `db/shift-repositories.ts` (сдача,
приёмка, отклонение, конфликт и сверка), движок синхронизации сам отправляет
`operation.entity_type` и применяет `merged_shift`, `applyChanges` кэширует смены.

## 4. UI S-15 «Смены»

Маршрут `/shifts`, пункт нижней навигации. Форма сдачи (журнал, дата, окно, комментарий),
список смен с фильтром статуса, кнопки «Принять смену»/«Отклонить» для входящего
руководителя (своя смена недоступна), отображение статуса синхронизации и конфликта
с кнопкой «Сверить с сервером», печатная форма акта сдачи-приёмки (стороны, окно,
число записей, замечания, места подписей).

## 6. Ограничения

- `SIGNATURE_PROVIDER=none` (по умолчанию вне production-профиля) — подписи не
  формируются; статус смены всё равно фиксируется, но юридическая значимость не
  заявляется (OQ-04).
- Форма акта и состав реквизитов смены требуют подтверждения владельцем процесса (903н).
- Увязка смены с нарядами/допусками, отчёт о смене и уведомления — вне t4.
- Конфликт смены разрешается принятием серверного состояния («Сверить с сервером»);
  отдельного журнала конфликтов смен нет.
