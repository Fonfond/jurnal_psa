## 1. Общие сведения и назначение системы

### 1.1. Назначение

ЭОЖ — это устанавливаемое на смартфон, планшет или ноутбук веб-приложение (PWA), предназначенное для оперативной фиксации фактов выполнения работ производственным и полевым персоналом с привязкой к нарядам-допускам. Приложение ДОЛЖНО полностью сохранять работоспособность основного сценария при отсутствии сети и автоматически синхронизировать накопленные данные при её появлении.

Система ДОЛЖНА обеспечивать:

1. Фиксацию записи о выполненной работе за минимальное число действий, преимущественно голосом.
2. Сохранение записи локально с гарантией, что подтверждённая пользователем запись не будет потеряна при закрытии приложения, перезагрузке устройства или длительном отсутствии сети.
3. Привязку записи к наряду-допуску с переходом в карточку наряда по ссылке.
4. Автоматическую и ручную синхронизацию с сервером с прозрачным для пользователя статусом каждой записи.
5. Просмотр, поиск и фильтрацию записей, в том числе офлайн.
6. Разграничение доступа по ролям и неизменяемый журнал аудита действий.

### 1.2. Проблематика (as-is → to-be)

| Аспект | Как есть (бумажный / файловый журнал) | Как должно быть (ЭОЖ) | Измеримый эффект |
|---|---|---|---|
| Фиксация факта работы | Запись от руки после работы, 2–5 минут на запись | Голосовая запись 10–40 секунд, сохранение в 1–2 действия | Сокращение времени фиксации не менее чем в 3 раза (KPI-02) |
| Полнота | Записи теряются, оформляются «задним числом», часть работ не фиксируется | Запись создаётся на месте; черновик не теряется; очередь синхронизации устойчива к сбоям | Доля записей, созданных в течение 15 минут после работы, не менее 80% |
| Связь с нарядом | Номер наряда переписывается вручную, возможны опечатки | Выбор из справочника, номер — гиперссылка на карточку наряда | Доля записей с корректной привязкой к наряду не менее 95% |
| Сверка и отчётность | Ручная сверка бумажных журналов, 1–3 дня на период | Данные на сервере в структурированном виде, выгрузка и фильтры | Сокращение трудозатрат руководителя на сверку не менее чем на 50% |
| Доступность данных | Журнал доступен только физически | Данные доступны на устройстве офлайн и на сервере онлайн | 100% доступность чтения офлайн за последние 30 дней |
| Аудит изменений | Отсутствует, исправления не отслеживаются | Неизменяемый журнал аудита с версиями записей | 100% изменений атрибутируются (кто, когда, что) |

| 2 | Справочник нарядов с офлайн-кэшем и карточкой наряда | MVP |
| 3 | Серверная часть: API, аутентификация, хранение, синхронизация, аудит | MVP |
| 4 | Роли и разграничение доступа (сотрудник, руководитель, администратор) | MVP |
| 5 | Административный интерфейс: справочники, пользователи, аудит, настройки | MVP (базовый) |
| 6 | Синхронизация справочников и записей между устройством и сервером | MVP |
| 7 | Установка PWA, работа офлайн, обновление версий | MVP |
| 8 | Вложения (фото), push-уведомления, расширенные отчёты | v1.1 |
| 9 | Интеграция с внешней системой нарядов в режиме записи (создание/закрытие наряда из ЭОЖ) | v2 |

**Не входит в объём (out of scope):**

| № | Исключение | Обоснование / возможный релиз |
|---|---|---|
| 1 | Электронная подпись и юридически значимый документооборот | Требует отдельного согласования с юристами; OQ-04 |
| 2 | Трекинг геолокации и постоянное определение местоположения | Избыточно для MVP, повышает расход батареи и риски приватности |
| 3 | Полноценный офлайн-просмотр PDF-документов наряда внутри приложения | В MVP — открытие кэшированного PDF системным просмотрщиком; встроенный просмотр — v1.1 |
| 4 | Видеозапись, потоковая передача аудио на сервер | Не требуется; аудио по умолчанию не хранится |
| 5 | Учёт рабочего времени, расчёт заработной платы, кадровый учёт | Отдельные системы, интеграция — v2 |
| 6 | Собственная модель распознавания речи (обучение) | Используются готовые модели; доменная адаптация — v1.1 |
| 7 | Мобильные нативные приложения (iOS/Android) | PWA покрывает целевые сценарии; нативные приложения — вне рассмотрения |
| 8 | Офлайн-шифрование базы данных с ключом от PIN | Повышает сложность и риск потери данных; v2 (см. RSK-07) |

### 1.4. Условия эксплуатации

| Фактор | Требование к системе |
|---|---|
| Работа в перчатках, на холоде, при ярком солнце | Тач-цели не менее 48×48 px, основные действия — в нижней трети экрана, контраст не ниже 4.5:1, светлая тема по умолчанию |
| Шум производственной среды (70–95 дБ) | Голосовой ввод ДОЛЖЕН работать с гарнитурой и без неё; при низком отношении сигнал/шум — предупреждение и предложение ручного ввода |
| Слабая и нестабильная связь (2G/3G, пропадания) | Все операции записи — локальные; сеть не блокирует UI; таймауты и повторные попытки |

| Устройства среднего ценового сегмента | Референсное устройство: Android 12+, 4 ГБ ОЗУ, 4-ядерный CPU класса Snapdragon 6xx; iPhone SE 2-го поколения и новее |
| Низкая квалификация части пользователей | Онбординг при первом запуске, подсказки, отсутствие модальных окон, блокирующих работу |
| Разные часовые пояса и неверные часы устройства | Модель времени устойчива к расхождению часов (см. п. 7.6) |

### 1.5. Допущения

| ID | Допущение | Влияние при нарушении |
|---|---|---|
| A-01 | У заказчика есть корпоративный Identity Provider (OIDC/SAML) либо он будет предоставлен к началу разработки | Меняется схема аутентификации, сроки MVP +2 недели |
| A-02 | Существует внешняя система учёта нарядов-допусков, из которой можно получать перечень нарядов по API или регулярной выгрузкой | Справочник нарядов придётся вести вручную в ЭОЖ (объём +3 недели) |
| A-03 | Персонал обеспечен устройствами с поддержкой современных браузеров (см. п. 9.5); доля неподдерживаемых устройств не превышает 5% | Требуется отдельная стратегия для устаревших устройств |
| A-04 | Электронная запись журнала признаётся заказчиком достаточной для внутреннего учёта; юридическая значимость не требуется в MVP | Блокирует запуск в эксплуатацию (OQ-04) |
| A-05 | Серверная инфраструктура размещается на территории РФ (или доступна с неё) | Требует пересмотра требований 152-ФЗ и закупки ресурсов |
| A-06 | У пользователей есть учетные записи в корпоративном домене; самостоятельная регистрация не требуется | Требуется модуль приглашений и подтверждения личности |
| A-07 | Внешняя система нарядов позволяет строить прямые ссылки (deep link) на карточку наряда | Ссылка на наряд открывает только кэшированную карточку ЭОЖ |
| A-08 | Голосовой ввод не является единственным способом: ручной ввод доступен всегда | Блокирует приёмку для iOS и устройств без поддержки WASM |

### 1.6. Ограничения

| ID | Ограничение |
|---|---|
| C-01 | Приложение ДОЛЖНО работать в браузере без установки нативных зависимостей; установка — через механизм «Установить приложение» (Add to Home Screen) |
| C-02 | Приложение ДОЛЖНО сохранять основной сценарий при отключённой сети; сетевые запросы НЕ ДОЛЖНЫ быть обязательными для создания записи |
| C-03 | Размер первоначальной загрузки (app shell) НЕ ДОЛЖЕН превышать 600 КБ в сжатом виде (gzip/brotli) |
| C-04 | Модель распознавания речи загружается отдельно от основного бандла и НЕ ДОЛЖНА входить в precache |
| C-05 | Приложение НЕ ДОЛЖНО использовать нестандартные браузерные API, недоступные в целевых браузерах (см. п. 9.5); при отсутствии API — обязательна деградация |
| C-06 | Приложение НЕ ДОЛЖНО хранить в открытом виде пароли, токены доступа в `localStorage` и персональные данные, не требуемые сценарием |
| C-07 | Максимальный объём локального хранилища, занимаемый приложением, НЕ ДОЛЖЕН превышать 250 МБ без явного действия пользователя (загрузка PDF, прикрепление фото) |

## 2. Термины и определения

| Термин | Определение |
|---|---|
| **Запись журнала** (entry) | Единица учёта: факт выполнения работы с датой/временем, текстовым описанием, типом работы, объектом и, при необходимости, привязкой к наряду |
| **Наряд-допуск** (permit) | Документ, разрешающий выполнение работ повышенной опасности; в системе — сущность со номером, статусом, периодом действия, объектом и участниками |
| **Оперативный журнал** | Упорядоченная по времени совокупность записей, доступная сотруднику и руководителю |
| **Автор записи** | Пользователь, создавший запись; по умолчанию не может быть изменён |
| **Исполнитель** | Участник работ, указанный в записи помимо автора (опционально) |
| **Черновик** | Локально сохраняемый ввод, ещё не превращённый в запись; переживает перезапуск приложения |
| **Outbox (очередь операций)** | Локальная очередь несинхронизированных операций (создание, изменение, удаление), переживающая перезапуск |
| **Операция** (op) | Атомарное изменение сущности, помещаемое в outbox: `create`, `update`, `delete` |
| **Идемпотентность** | Свойство операции давать один и тот же результат при повторной отправке; обеспечивается уникальным `op_id` |
| **HLC** (Hybrid Logical Clock) | Гибридные логические часы: пара «физическое время + логический счётчик», устойчивая к расхождению часов устройств |
| **LWW** (Last-Write-Wins) | Стратегия разрешения конфликтов «побеждает последняя запись», применяемая на уровне отдельного поля |
| **Версия записи** (version) | Монотонно возрастающий номер серверной ревизии записи; используется для оптимистической блокировки |
| **Оптимистическая блокировка** | Механизм, при котором клиент присылает `base_version`, а сервер отклоняет изменение при расхождении |
| **App Shell** | Минимальный набор HTML/CSS/JS и ресурсов, обеспечивающий запуск интерфейса без сети |
| **Service Worker (SW)** | Фоновый скрипт браузера, перехватывающий сетевые запросы и обеспечивающий кэширование и фоновую синхронизацию |
| **Background Sync** | Браузерный API отложенной синхронизации, выполняемой при появлении сети (Chromium) |
| **Periodic Background Sync** | Браузерный API периодической фоновой синхронизации (Chromium, установленное приложение) |
| **Cold start** | Запуск приложения при отсутствии активного процесса (после закрытия или выгрузки из памяти) |
| **TTI** (Time to Interactive) | Время от начала загрузки до состояния, когда интерфейс отвечает на действия пользователя |
| **On-device ASR** | Распознавание речи, выполняемое целиком на устройстве без передачи аудио в сеть |
| **Web Speech API** | Браузерный API распознавания речи; в большинстве реализаций аудио обрабатывается на серверах вендора |
| **WER** (Word Error Rate) | Доля ошибочно распознанных слов; метрика качества распознавания |
| **RTF** (Real-Time Factor) | Отношение времени распознавания к длительности аудио; RTF ≤ 1 означает обработку быстрее реального времени |
| **Смена** | Период работы бригады/сотрудника, используемый для группировки записей |
| **Объект / участок** | Производственный объект или участок, к которому относится работа |
| **Референсное устройство** | Устройство, на котором измеряются все числовые показатели производительности (см. п. 9.1.2) |
| **Tombstone** | Признак удаления сущности, передаваемый при синхронизации вместо физического удаления |
| **Аудит** | Неизменяемая запись событий системы: кто, когда, что изменил, с какими значениями до и после |
| **Роль** | Набор прав пользователя: сотрудник, руководитель, администратор |
| **PWA** | Progressive Web App — веб-приложение с манифестом, service worker и установкой на устройство |

## 3. Цели и критерии успеха (KPI)

### 3.1. Цель продукта

Обеспечить фиксацию факта выполненной работы за время, не превышающее 40 секунд для типовой записи, силами сотрудника на месте работ, без зависимости от качества связи, с сохранением полной истории и связи с нарядами.

### 3.2. Продуктовые KPI

| ID | Метрика | Способ измерения | Baseline | Цель MVP | Цель v1.1 |
|---|---|---|---|---|---|
| KPI-01 | Доля записей, созданных голосом | Аналитика клиента: `input_method = voice` / все записи | 0% (бумажный журнал) | ≥ 60% | ≥ 75% |
| KPI-02 | Медианное время создания записи (от нажатия «Создать» до «Сохранить») | Клиентская телеметрия, P50/P90 | 120–300 с (бумага) | P50 ≤ 40 с, P90 ≤ 90 с | P50 ≤ 30 с, P90 ≤ 60 с |
| KPI-03 | Доля записей, сохранённых без последующей правки текста | Счётчик правок на запись за 24 ч | — | ≥ 80% | ≥ 88% |
| KPI-04 | Потеря подтверждённых записей | Инциденты + сверка локального и серверного журналов | — | 0 случаев | 0 случаев |
| KPI-05 | Доля записей, синхронизированных в течение 24 ч после появления сети | Серверная аналитика по `received_at` | — | ≥ 99% | ≥ 99,5% |
| KPI-06 | Задержка синхронизации после появления сети | P95 интервала «сеть появилась → `received_at`» | — | ≤ 120 с | ≤ 60 с |

### 4.4. Ключевые сценарии

**Сценарий S-1. Голосовая запись офлайн (основной)**

1. Сотрудник открывает приложение (офлайн, холодный старт ≤ 3 с) и нажимает кнопку «+».
2. Приложение открывает экран создания записи с уже заполненными полями: дата/время = сейчас, автор = текущий пользователь, объект = последний использованный.
3. Сотрудник нажимает кнопку микрофона, диктует: «Заменил участок трубопровода на третьем стояке, наряд сто двадцать три дробь двадцать пять, работал с девяти до одиннадцати».
4. Приложение записывает аудио, показывает индикатор уровня и таймер; повторное нажатие останавливает запись.
5. Запускается распознавание на устройстве (прогресс, возможность отмены); по завершении текст появляется в редактируемом поле.
6. Приложение выделяет в тексте номер наряда, сверяет со справочником и предлагает привязку: «Найден наряд НД-123/2025 — привязать?».
7. Сотрудник подтверждает привязку, при необходимости правит текст и время («с 9:00 до 11:00» → предлагается `performed_at = 11:00` с комментарием), нажимает «Сохранить».
8. Запись и операция `create` атомарно сохраняются в локальной базе; в списке появляется запись со статусом «Ожидает синхронизации».
9. Через 20 минут появляется сеть; приложение автоматически отправляет очередь; статус меняется на «Синхронизирована», пользователь видит ненавязчивое подтверждение.

**Сценарий S-2. Ручной ввод при недоступности голоса**

1. Приложение определяет, что on-device модель не загружена и сети нет; кнопка микрофона неактивна с пояснением «Голосовой ввод недоступен офлайн: модель не загружена. Загрузить сейчас?».
2. Сотрудник выбирает «Ввести вручную», заполняет поля, использует подсказки типовых формулировок.
3. Сохранение и синхронизация происходят по общему сценарию.

**Сценарий S-3. Конфликт при синхронизации**

1. Сотрудник A офлайн изменил текст записи; руководитель B в это же время изменил тот же текст на сервере.
2. При синхронизации сервер возвращает `409` с текущей версией и значениями полей.
3. Клиент применяет полевое LWW по HLC, сохраняет проигравшее значение в историю ревизий и показывает на карточке бейдж «Изменено руководителем» с возможностью посмотреть обе версии.
4. Если конфликт затронул обязательное поле и разрешить автоматически невозможно — запись переходит в статус «Конфликт», пользователю показывается экран разрешения (S-13, п. 8.2).

**Сценарий S-4. Работа с нарядом**

1. Сотрудник открывает вкладку «Наряды»; список доступен офлайн из кэша (активные наряды сотрудника и участка).
2. Открывает карточку наряда: номер, статус, срок действия, объект, описание работ, ответственные.
3. Нажимает «Открыть в системе» — при наличии сети открывается внешняя система; офлайн показывается сообщение и кнопка «Открыть при появлении сети» (задача ставится в очередь).
4. Из карточки наряда может создать связанную запись — наряд предзаполнен.

### 4.5. Ограничения по использованию

- `FR-USE-01` (MVP, M). Приложение ДОЛЖНО использоваться только авторизованными пользователями; гостевой режим отсутствует.
- `FR-USE-02` (MVP, M). Один пользователь МОЖЕТ использовать несколько устройств; записи синхронизируются между ними через сервер.
- `FR-USE-03` (MVP, M). Одновременное редактирование одной записи на двух устройствах ДОЛЖНО разрешаться по правилам п. 7.7, а не блокироваться.

## 6. Модель данных

### 6.1. Принципы

1. **Идентификаторы.** Все сущности, создаваемые клиентом, получают идентификатор UUID v7, сгенерированный на устройстве до сохранения. Идентификатор неизменяем и не переиспользуется.
2. **Два источника времени.** `created_at_client` / `updated_at_client` — часы устройства (могут быть неверны); `created_at_server` / `updated_at_server` — авторитетные серверные метки, проставляемые при получении. Бизнес-время (`performed_at`) хранится отдельно и не зависит от обоих.
3. **Мягкое удаление.** Физическое удаление данных запрещено для записей, нарядов, пользователей и справочников; используется `deleted_at` + tombstone для синхронизации.
4. **Версионирование.** Каждая синхронизируемая сущность имеет `version` (целое, увеличивается сервером на 1 при каждом изменении) и `hlc` (для разрешения конфликтов на уровне полей).
5. **Нормализация.** Справочники вынесены в отдельные сущности; в записи хранятся только ссылки. Дублирование наименований в записи не допускается.
6. **Локальность.** На клиенте хранятся только данные, необходимые для офлайн-работы: записи пользователя (и подразделения — для руководителя), справочники, наряды из кэша, PDF по запросу.
7. **Никаких «умных» вычисляемых полей на клиенте**, влияющих на синхронизацию: все производные значения (например, признак «просрочено») вычисляются на сервере или в момент отображения.

| `Device` | `id`, `user_id`, `name`, `platform`, `app_version`, `user_agent`, `push_subscription` (json), `created_at`, `last_seen_at`, `status` | Не более 5 активных устройств на пользователя; при превышении — самое старое требует повторного входа |
| `Draft` | `id`, `user_id`, `entry_id` (nullable), `payload` (json ≤ 16 КБ), `updated_at`, `device_id` | Хранится только локально; не более 20 черновиков на пользователя, старые вытесняются |
| `SyncState` | `key`, `cursor`, `last_success_at`, `last_attempt_at`, `server_time_offset_ms`, `dictionary_versions` (json) | Хранится только локально |
| `Attachment` (v1.1) | `id`, `entry_id`, `kind` (`photo` \| `document`), `mime`, `size_bytes` (≤ 5 МБ), `sha256`, `width`, `height`, `status` (`local` \| `uploading` \| `uploaded` \| `error`), `remote_url`, `created_at`, `uploaded_at` | Не более 5 вложений на запись; суммарно ≤ 20 МБ |
| `ConflictRecord` (v1.1) | `id`, `entry_id`, `field`, `local_value`, `remote_value`, `local_hlc`, `remote_hlc`, `resolution` (`local` \| `remote` \| `manual`), `resolved_by`, `resolved_at` | Создаётся только при неавтоматически разрешимом конфликте |

### 6.12. Правила валидации

Правила применяются на клиенте до сохранения и повторно на сервере. Расхождение трактуется как дефект: клиент обязан отклонять то же, что и сервер.

| Код | Правило | Уровень | Сообщение пользователю |
|---|---|---|---|
| R-01 | `text` обязателен, 10–2000 символов после обрезки | Ошибка | «Опишите работу: от 10 до 2000 символов» |
| R-02 | `work_type_id` обязателен и активен | Ошибка | «Выберите тип работ» |
| R-03 | `site_id` обязателен и активен | Ошибка | «Выберите объект» |

| R-05 | `permit_id` и `permit_number_raw` не могут быть заполнены одновременно | Ошибка | Техническая ошибка формы |
| R-06 | Наряд со статусом `annulled` запрещён | Ошибка | «Наряд аннулирован, привязка невозможна» |

| R-11 | `author_id` неизменяем | Ошибка сервера | «Автор записи не может быть изменён» |

| R-17 | Удалённую запись нельзя редактировать | Ошибка | «Запись удалена» |
| R-18 | `version` при обновлении должен совпадать с серверной (оптимистическая блокировка) | Ошибка `409` | «Запись изменена на другом устройстве» |

| R-23 | Пользователь активен | Ошибка `403` | «Учётная запись недоступна» |

### 7.2. Клиентские слои

| Слой | Ответственность | Ключевые ограничения |
|---|---|---|
| UI / App Shell | Экраны, навигация, доступность, локализация | Начальная загрузка ≤ 600 КБ (gzip), TTI ≤ 3 с офлайн |
| Domain | Правила валидации, бизнес-операции, состояние | Не содержит сетевых вызовов напрямую; работает только с локальным хранилищем |
| Local Store | IndexedDB: записи, ревизии, справочники, наряды, outbox, черновики, sync state | Все записи изменений — в транзакциях; схема версионируется |
| Sync Engine | Отправка outbox, приём изменений (pull), разрешение конфликтов, backoff | Не блокирует UI; идемпотентность; журналирование |
| Voice Engine | Запись аудио, выбор движка ASR, постобработка текста | Работает в Web Worker; не блокирует UI; аудио не сохраняется |
| Auth / Session | Вход, обновление сессии, офлайн-срок, роли | Токены не в `localStorage`; корректное поведение при `401` |
| Service Worker | Кэширование, офлайн-навигация, Background Sync | Не кэширует API-ответы с персональными данными бессрочно |

**Требования к слоям:**

- `FR-ARC-01` (MVP, M). Domain-слой НЕ ДОЛЖЕН обращаться к сети; все сетевые операции выполняются Sync Engine.
- `FR-ARC-02` (MVP, M). Схема IndexedDB ДОЛЖНА версионироваться; миграция ДОЛЖНА быть обратимо-безопасной (сначала резервная копия критичных данных в отдельное хранилище, затем миграция, затем удаление копии).
- `FR-ARC-03` (MVP, M). Миграция НЕ ДОЛЖНА блокировать интерфейс дольше 2 с; при превышении — выполняться в фоне с индикатором.
- `FR-ARC-04` (MVP, M). Кэш Service Worker НЕ ДОЛЖЕН содержать ответы API с текстом записей; данные записей хранятся только в IndexedDB.
- `FR-ARC-05` (v1.1, S). Тяжёлые операции (поисковый индекс, распознавание) ДОЛЖНЫ выполняться в Web Worker.

### 7.3. Путь записи (write path)

1. Пользователь заполняет форму; валидация выполняется на клиенте (правила раздела 6.12).
2. При сохранении Domain-слой формирует объект записи (`id`, `hlc`, `created_at_client`) и операцию (`op_id`, `op_type = create`, `payload`).
3. В одной транзакции IndexedDB записываются: сущность `entries`, операция `outbox`, при необходимости — ревизия `revisions`.
4. UI немедленно обновляется оптимистично: запись появляется в ленте со статусом `pending`.
5. Sync Engine получает сигнал о новой операции и, если сеть доступна, запускает отправку; если нет — операция остаётся в очереди.
6. После ответа сервера (`applied`) запись обновляется: `version`, `created_at_server`, `sync_status = synced`; операция удаляется из outbox.
7. При ошибке операция остаётся в outbox с `next_attempt_at`; UI показывает статус `error` после исчерпания автоматических попыток.

**Требование:** шаг 3 ДОЛЖЕН быть атомарным; шаги 4–7 НЕ ДОЛЖНЫ требовать участия пользователя.

### 7.4. Протокол синхронизации

#### 7.4.1. Состав API

| Метод | Путь | Назначение | Идемпотентность |
|---|---|---|---|
| `POST` | `/v1/auth/session` | Обновление сессии | Нет |
| `POST` | `/v1/auth/logout` | Завершение сессии | Да |
| `GET` | `/v1/me` | Профиль, роль, подразделение, настройки | Да |
| `GET` | `/v1/entries` | Список записей (пагинация, фильтры) | Да |
| `GET` | `/v1/entries/{id}` | Запись с ревизиями | Да |
| `POST` | `/v1/sync/push` | Отправка батча операций | Да (по `op_id`) |
| `GET` | `/v1/sync/pull` | Получение изменений по курсору | Да |
| `GET` | `/v1/permits` | Наряды (инкрементально) | Да |
| `GET` | `/v1/permits/{id}` | Карточка наряда | Да |
| `POST` | `/v1/permits/{id}/pdf-url` | Подписанная ссылка на PDF | Да |
| `GET` | `/v1/dictionaries` | Справочники и их версии | Да |
| `GET` | `/v1/audit` | Журнал аудита (admin/supervisor) | Да |
| `POST` | `/v1/admin/users`, `PATCH /v1/admin/users/{id}` | Управление пользователями | Нет |
| `GET` | `/v1/health` | Проверка доступности | Да |

**Общие требования к API:**

- `FR-API-01` (MVP, M). Формат — JSON UTF-8; сжатие `gzip`/`br`; HTTP/2.
- `FR-API-02` (MVP, M). Версионирование в пути (`/v1/`); сервер ДОЛЖЕН поддерживать текущую и предыдущую мажорные версии клиента не менее 90 дней.
- `FR-API-03` (MVP, M). Каждый ответ ДОЛЖЕН содержать `server_time` (UTC, ISO 8601 с миллисекундами) и `request_id`.
- `FR-API-04` (MVP, M). Ошибки ДОЛЖНЫ возвращаться в едином формате: `code`, `message`, `fields` (для валидации), `request_id`.
- `FR-API-05` (MVP, M). `POST /v1/sync/push` ДОЛЖЕН принимать не более 50 операций и не более 1 МБ тела запроса; при превышении — `413`.
- `FR-API-06` (MVP, M). Все изменяющие запросы ДОЛЖНЫ быть защищены от CSRF и проверять права на сервере.
- `FR-API-07` (MVP, M). Пагинация — курсорная (`cursor`, `limit` ≤ 100), без `offset` для больших выборок.

#### 7.4.2. Контракт push (требования к структуре)

Запрос содержит: `device_id`, `app_version`, `ops[]`. Каждая операция содержит: `op_id`, `entity_type`, `entity_id`, `op_type`, `base_version`, `hlc`, `payload` (поля сущности), `client_time`.

Ответ содержит: `server_time`, `results[]`, `next_pull_cursor`. Каждый результат содержит: `op_id`, `status` (`applied`, `duplicate`, `conflict`, `rejected`), `version`, `entry` (актуальное состояние при успехе или конфликте), `error` (`code`, `message`, `fields`).

**Требования:**

- `FR-API-08` (MVP, M). Сервер ДОЛЖЕН обрабатывать операции батча независимо: ошибка одной операции НЕ ДОЛЖНА откатывать остальные.
- `FR-API-09` (MVP, M). Повторная операция с тем же `op_id` ДОЛЖНА возвращать `duplicate` и результат первой обработки без повторного применения.
- `FR-API-10` (MVP, M). Порядок применения операций над одной сущностью ДОЛЖЕН соответствовать порядку `hlc`; при нарушении порядка сервер ДОЛЖЕН вернуть `conflict`.
- `FR-API-11` (MVP, M). Сервер ДОЛЖЕН сохранять клиентское время операции в аудите, но использовать для `created_at_server` собственное время получения.

#### 7.4.3. Контракт pull

Ответ содержит: `server_time`, `cursor`, `entries[]` (включая tombstones), `permits[]`, `dictionaries[]`, `has_more`.

- `FR-API-12` (MVP, M). Курсор ДОЛЖЕН быть непрозрачной строкой; клиент НЕ ДОЛЖЕН его интерпретировать.
- `FR-API-13` (MVP, M). Размер страницы pull — до 200 сущностей; при `has_more = true` клиент ДОЛЖЕН продолжать запросы до получения полного набора.
- `FR-API-14` (MVP, M). Удалённые сущности ДОЛЖНЫ передаваться как tombstone с идентификатором и временем удаления; клиент ДОЛЖЕН удалять их локально, сохраняя аудит.

#### 7.4.4. Порядок синхронизации

1. Проверка сессии (`401` → обновление/вход).
2. `pull` изменений справочников и нарядов.
3. `push` операций из outbox (батчами).
4. `pull` изменений записей (включая результаты собственного push и изменения с других устройств).
5. Обновление `SyncState`, сводного индикатора и журнала синхронизации.

**Требование:** шаг 3 и шаг 4 НЕ ДОЛЖНЫ выполняться одновременно для одной сущности; при конфликте результатов приоритет имеет серверное состояние после слияния.

### 7.5. Состояния операции и повторные попытки

```
pending ──(сеть есть)──► in_flight ──(applied)──► удалена из очереди
   ▲                        │
   │                        ├──(409)──► conflict ──► слияние (7.7) ──► pending/удалена
   │                        ├──(4xx кроме 408/429)──► dead (ручной разбор)
   │                        ├──(5xx/сеть)──► pending (next_attempt_at = now + backoff)
   └────────────────────────┴──(10 попыток)──► dead
```

**Требования:**

- `FR-SYN-29` (MVP, M). `in_flight`-операции при аварийном завершении приложения ДОЛЖНЫ возвращаться в `pending` при следующем запуске (по отсутствию `ack_at`).
- `FR-SYN-30` (MVP, M). Backoff ДОЛЖЕН учитывать `Retry-After` при `429`; при отсутствии заголовка — экспоненциальная задержка по п. FR-SYN-08.
- `FR-SYN-31` (MVP, M). Ручной повтор операции ДОЛЖЕН сбрасывать счётчик попыток и статус в `pending`.
- `FR-SYN-32` (v1.1, S). Операции в статусе `dead` ДОЛЖНЫ отображаться отдельным списком с возможностью экспорта payload для диагностики.

### 7.6. Модель времени

| Понятие | Назначение | Источник | Изменяемость |
|---|---|---|---|
| `performed_at` | Бизнес-время выполнения работы | Пользователь / устройство | Да, с причиной |
| `performed_tz_offset_min` | Смещение пояса места работы | Устройство на момент записи | Нет |
| `created_at_client` / `updated_at_client` | Время создания/изменения на устройстве | Часы устройства | Нет |
| `created_at_server` / `updated_at_server` | Авторитетное время | Сервер | Нет |
| `hlc` | Порядок событий и разрешение конфликтов | Устройство + сервер | Только вперёд |
| `server_time` | Оценка серверного времени | Ответ API | Пересчитывается |

**Алгоритм HLC (требование, не код):**

- Каждое устройство хранит пару `(physical_ms, counter)`.
- При локальном событии: `physical = max(now, last_physical)`; если `physical == last_physical`, `counter++`, иначе `counter = 0`.
- При получении серверного/чужого HLC: `physical = max(now, last_physical, remote_physical)`; счётчик корректируется так, чтобы новое значение было строго больше обоих.
- HLC форматируется как строка фиксированной ширины, чтобы лексикографическое сравнение совпадало с хронологическим.

**Требования:**

- `FR-TIME-01` (MVP, M). Расхождение часов устройства с сервером ДОЛЖНО определяться по `server_time` при каждом успешном запросе; при превышении 2 минут — предупреждение в интерфейсе.
- `FR-TIME-02` (MVP, M). Корректировка `performed_at` по серверному времени ДОЛЖНА выполняться только с согласия пользователя и фиксироваться как `server_corrected` с причиной.
- `FR-TIME-03` (MVP, M). Переход на летнее время и смена часового пояса НЕ ДОЛЖНЫ изменять отображаемое бизнес-время ранее созданных записей (используется `performed_tz_offset_min`).
- `FR-TIME-04` (MVP, M). Записи, созданные офлайн, ДОЛЖНЫ сохранять корректный порядок в ленте даже при неверных часах устройства (сортировка по `performed_at`, при равенстве — по `hlc`).

### 7.7. Разрешение конфликтов

Стратегия: **полевое LWW с приоритетом роли и версионированием**. Конфликт фиксируется, когда серверная версия отличается от `base_version` операции.

**Приоритет при равном времени:** `admin` > `supervisor` > `worker`. При равном приоритете побеждает большее значение HLC. Проигравшее значение НЕ теряется: оно записывается в `EntryRevision` с `source = conflict_resolution`.

| № | Ситуация | Правило разрешения | Что видит пользователь |
|---|---|---|---|
| C-01 | Разные поля изменены на разных устройствах | Автоматическое слияние: каждое поле берётся из более поздней правки | «Изменения объединены» |
| C-02 | Одно и то же поле изменено автором на двух устройствах | LWW по HLC | Бейдж «Изменено на другом устройстве», история доступна |
| C-03 | Поле изменено автором и руководителем | Побеждает руководитель (приоритет роли), независимо от HLC | «Изменено руководителем», причина в истории |
| C-04 | Удаление на одном устройстве, изменение на другом | Побеждает удаление (tombstone); изменение сохраняется в аудите | Запись отсутствует в списке; администратор может восстановить |
| C-05 | Удаление руководителем, восстановление автором | Приоритет руководителя; восстановление только администратором | Сообщение «Запись удалена руководителем» |
| C-06 | Одновременное создание с одинаковым `id` (аномалия) | Сервер отклоняет вторую операцию как `conflict`, данные не теряются | Ошибка, запись сохраняется локально как `dead` для разбора |
| C-07 | Изменение `performed_at` вручную и серверная коррекция | Побеждает более позднее по HLC; причина обязательна | Пометка «Время скорректировано» |
| C-08 | Привязка к наряду, который стал `annulled` | Автоматически не разрешается; запись переходит в `conflict` | Экран S-13: выбрать другой наряд или оставить с пометкой |
| C-09 | Слияние привело к невалидному состоянию (пустой текст, отсутствует обязательное поле) | Автоматически не разрешается; запись в `conflict` | Экран S-13 с подсветкой полей |
| C-10 | Конфликт версий при `update` от другого устройства без локальных изменений | Применяется серверная версия | Без уведомления |

**Требования:**

- `FR-CNF-01` (MVP, M). При конфликте НЕ ДОЛЖНА происходить потеря данных: проигравшие значения сохраняются в ревизиях.
- `FR-CNF-02` (MVP, M). Запись в статусе `conflict` ДОЛЖНА быть видима в списке и в очереди синхронизации.
- `FR-CNF-03` (MVP, M). Разрешение конфликта вручную ДОЛЖНО фиксироваться в аудите с указанием выбранного варианта.
- `FR-CNF-04` (v1.1, S). Для конфликтов, разрешённых автоматически, ДОЛЖНА быть доступна сводка «что изменилось» за период.

### 7.8. Голосовой модуль

**Конвейер:** `getUserMedia` → `AudioWorklet` (ресемплинг в 16 кГц, моно) → буфер → VAD (опционально, обрезка тишины) → адаптер ASR → постобработка (пунктуация, числа, извлечение номера наряда и времени) → редактируемое поле.

| Компонент | Требование |
|---|---|
| Захват аудио | `MediaRecorder` (Opus/WebM) или `AudioWorklet` с PCM; при отсутствии `AudioWorklet` — `MediaRecorder`; минимальная поддерживаемая частота дискретизации — 16 кГц |
| On-device ASR | Whisper-совместимая модель, скомпилированная в WebAssembly, работающая в Web Worker; квантованная модель ≤ 50 МБ; кэш в Cache Storage с проверкой SHA-256 |

| Постобработка | Нормализация чисел и дат, расстановка заглавных букв и пунктуации (правилами), извлечение номера наряда (регулярное выражение + нормализация + сверка со справочником), извлечение времени (v1.1) |
| Отмена | Прерывание распознавания в течение 5 с без частичного результата |

### 7.9. Аутентификация и сессии (архитектурный уровень)

1. Вход: редирект на IdP (OIDC Authorization Code + PKCE) либо форма логина; после успеха сервер устанавливает HttpOnly Secure SameSite=Lax cookie сессии и возвращает профиль и роль.
2. Access-токен (если используется Bearer-схема) живёт ≤ 15 минут и хранится в памяти вкладки; refresh — в HttpOnly cookie.
3. Офлайн: клиент хранит зашифрованную (средствами браузера) запись о сессии с `offline_valid_until`; при отсутствии сети доступ определяется ею.
4. `401` при синхронизации: однократная попытка обновления; при неудаче — статус «Требуется вход», очередь сохраняется, данные не удаляются.
5. Выход: очистка токенов, кэша сессии и (по подтверждению) локальных данных; очередь при этом должна быть пуста либо экспортирована.

## 8. Требования к интерфейсу

### 8.1. Общие принципы

1. **Одно главное действие на экран.** На экране создания записи главное действие — микрофон; на ленте — кнопка «+»; в карточке — «Синхронизировать»/«Изменить» по контексту.
2. **Никаких тупиков.** Любое состояние ошибки содержит действие («Повторить», «Ввести вручную», «Синхронизировать») или объяснение, что делать.
3. **Статус всегда виден.** Пользователь в любой момент понимает: есть ли сеть, сколько записей не отправлено, синхронизирована ли конкретная запись.
4. **Офлайн — норма, а не ошибка.** Отсутствие сети НЕ ДОЛЖНО оформляться как критическая ошибка или блокирующее модальное окно.
5. **Минимум модальных окон.** Подтверждения — только для необратимых или потенциально опасных действий (удаление, выход с очередью, обновление с непустой очередью).
6. **Крупные элементы.** Тач-цели ≥ 48×48 px, основной текст ≥ 16 px, отступы между интерактивными элементами ≥ 8 px.
7. **Цвет не единственный носитель информации.** Каждый статус дублируется иконкой и текстом.

### 10.1. Подход

Разработка ведётся итерациями по 2 недели с демонстрацией результата заказчику. Приоритет — сквозные сценарии, а не «слои»: каждая итерация должна давать проверяемый пользовательский результат. Функциональность, не входящая в MVP, не разрабатывается до приёмки MVP, но архитектурно не блокируется.

### 10.3. Состав MVP

MVP ДОЛЖЕН включать:

1. Вход, роли, офлайн-сессия, выход с защитой очереди.
2. Создание, просмотр, редактирование, удаление записей; валидация; черновики; подсказки и шаблоны.
3. Голосовой ввод на устройстве (русский язык) с загрузкой модели и деградацией до ручного ввода; Web Speech как резерв при наличии сети.
4. Справочник нарядов офлайн, карточка наряда, кликабельный номер, сохранение PDF по запросу.
5. Офлайн-хранилище, очередь операций, автоматическая и ручная синхронизация, статусы, разрешение конфликтов, идемпотентность.
6. Список, фильтры, поиск по тексту, счётчики.
7. Администрирование: справочники, пользователи, аудит, настройки.
8. Установка PWA, офлайн-навигация, обновление без потери данных.
9. Аудит действий, разграничение прав на сервере.

**MVP НЕ ДОЛЖЕН включать:** фото, push, отчёты, сохранённые фильтры, PIN, серверный поиск, распознавание времени, шифрование БД, геолокацию.

## 11. Критерии приёмки

### 11.1. Общие правила

1. Приёмка проводится по модулям; модуль принимается только при прохождении всех его пунктов (100%).
2. Каждый пункт проверяется на референсном устройстве и в целевом браузере, если не указано иное.
3. Дефекты классифицируются: `blocker` (блокирует приёмку), `critical`, `major`, `minor`. Модуль НЕ МОЖЕТ быть принят при наличии открытых `blocker`/`critical`.
4. Проверки, требующие сети, выполняются в двух режимах: онлайн и офлайн (авиарежим), если не указано иное.
5. Результаты оформляются протоколом с указанием устройства, версии браузера, версии приложения и идентификаторов требований.
6. Автотесты (e2e) ДОЛЖНЫ быть воспроизводимы в CI; ручные проверки — по чек-листу с отметкой исполнителя.
