## 4. Потоки данных

### 4.1. Создание записи (офлайн и онлайн — один путь)

```
UI → Domain.validate → EntryRepository.beginTx
   → entries.put(entry) + outbox.put(op) + revisions.put(rev) → commit
   → UI: optimistic status=pending
   → SyncEngine.wake()
```

Если сети нет — операция остаётся в `pending`; UI не блокируется.

### 4.2. Push

```
SyncEngine → MultiTabLock.acquire → batch = outbox.pending(limit=50, sort=hlc)
  → POST /sync/push {ops}
  → for each result:
       applied   → entries.update(version, server fields), outbox.delete
       duplicate → outbox.delete, entries.update(current)
       conflict  → ConflictService.apply(merged_entry), outbox.delete, mark conflict
       rejected  → outbox.status=dead (кроме retryable), UI error
  → SyncState.last_success_at, telemetry
```

### 4.3. Pull

```
GET /dictionaries/snapshot (если версия отличается) → atomic swap справочников
GET /sync/changes?since_seq=<cursor>&limit=200
  → apply permits (upsert/tombstone)
  → apply entries:
        if entry has pending local op → сохранить remote_snapshot, показать в карточке; merge НЕ выполняется
        else → upsert
  → cursor = response.next_seq; repeat while has_more
```

Слияние выполняет только сервер при `push` (ADR-04). Клиент применяет готовый `merged_entry`.

### 4.4. Разрешение конфликта

```
client push(op, base_version, field_clocks)
  → server: current_row.version != base_version
      → server_merge(current, op) по правилам C-01…C-12
      → response: status=conflict, merged_entry, resolution={field: local|remote}, conflicts[]
  → client: entries.put(merged_entry), ConflictRecord для полей с resolution=manual
  → UI: бейдж или экран разбора
```

### 4.5. Голосовой ввод

```
tap → getUserMedia → AudioWorklet/MediaRecorder → chunks(20s, overlap 2s)
  → Worker: ASR(adapter) → text parts → merge → normalize(numbers, punctuation)
  → editable field (no autosave)
  → save: input_method=voice, asr_engine, asr_confidence
```

При сворачивании: `visibilitychange` → стоп записи, сохранение черновика, уведомление.

### 4.6. Аутентификация и офлайн-сессия

```
login (OIDC PKCE) → server sets HttpOnly cookie → profile+role
offline: AppSession{offline_valid_until=+30d, device_id, role}
write: allowed always (local)
sync: requires valid session; 401 → refresh; refresh fail → "Требуется вход"
```

### 4.7. Обновление приложения

```
SW detects new version → downloads → waiting
UI banner → user confirms → if outbox not empty: postpone
→ activate → migration (with backup) → reload
```

### 4.8. Миграция схемы

```
backup critical stores → openDB(newVersion) → upgrade() in transaction
  → success: delete backup
  → failure: restore from backup, stay on old version, report
```

## 5. Механизм синхронизации

### 5.1. Состояния операции

```
pending ──claim──▶ in_flight ──applied──▶ удалена из очереди
   ▲                   │
   │                   ├─duplicate──▶ удалена из очереди
   │                   ├─conflict───▶ удалена из очереди + ConflictRecord
   │                   ├─rejected───▶ dead (manual)
   │                   └─retryable──▶ pending (next_attempt_at)
   └───────────────────────────────────┘
```

`in_flight` и `dead` — статусы операции; `synced`/`conflict`/`error` — статусы записи (`JournalEntry.sync_status`). Успешно применённая операция не хранится в очереди.

### 5.2. Правила

| Правило | Описание |
|---|---|
| Единственный путь записи | Все мутации PWA — `POST /sync/push` |
| Порядок | Внутри сущности — по `hlc`; между сущностями не гарантируется |
| Идемпотентность | `op_id` уникален; сервер хранит ответ 30 дней |
| Батч | ≤ 50 операций, ≤ 1 МБ, таймаут 30 с |
| Параллелизм | До 3 батчей одновременно, приоритет новым операциям; все операции одной сущности — в одном батче (при > 50 — последовательно) |
| Backoff | 2–15 мин, джиттер ±20%, `Retry-After` при 429, максимум 10 попыток |
| Зависимые операции | При `dead` для `create` — зависимые `update`/`delete` тоже `dead` |
| Мультивкладка | Web Locks; вторая вкладка показывает «синхронизация в другой вкладке» |
| Мультиустройство | Полевые часы + серверный merge |
| Восстановление | `in_flight` без `ack_at` → `pending` при старте |
| Курсор | `seq` из `change_log`, непрозрачен для клиента |
| Tombstone | 90 дней; при устаревшем курсоре — полный resync |
| Часы | HLC фиксированной ширины; `clock_anomaly` при дрейфе > 5 мин |

### 5.3. Серверный merge (алгоритм)

1. Проверить права и статус сущности.
2. Найти текущую строку; если `version == base_version` — применить как обычно.
3. Иначе для каждого поля из `payload`:
   - если поле не менялось после `base_version` — применить;
   - если менялось — сравнить HLC; при равенстве — приоритет роли только для проверенной записи;
   - если правило не даёт однозначного результата — `resolution = manual`.
4. Записать ревизию с diff и проигравшими значениями.
5. Увеличить `version`, записать в `change_log`.
6. Вернуть `merged_entry`, `resolution`, `conflicts[]`.

## 8. Интеграция с нарядами

### 8.1. Схема

```
Внешняя система ──API/файл──▶ PermitImportAdapter ──▶ PermitService ──▶ permit, change_log
                                     │
                                     ├─ normalize (номера, статусы, даты)
                                     ├─ validate (обязательные поля)
                                     └─ quarantine (ошибки → журнал импорта)
```

### 8.2. Требования к адаптеру

| Требование | Значение |
|---|---|
| Идемпотентность | Ключ `(source_id, external_id)` |
| Частота | Не реже 1 раза в сутки; по событию — если есть webhook |
| Удаление | Помечать `is_deleted`, не удалять физически |
| Изменение | Обновлять `updated_at_external`, версия |
| Deep link | Формируется адаптером; при отсутствии — `null` |
| Ошибки | Не прерывают импорт; попадают в журнал и карантин |
| Ручной режим | CSV/XLSX с тем же контрактом полей |

### 8.3. Временный режим без API

Администратор загружает CSV с колонками: `external_id, number, year, type, status, valid_from, valid_to, site_code, description, responsible_login, external_url, pdf_url`. Импорт идемпотентен, ошибки — в журнале.

### 9.1. Механизмы защиты данных (M-01…M-09)

| ID | Механизм | Реализация |
|---|---|---|
| M-01 | Атомарная транзакция | Запись + операция + ревизия в одной транзакции IDB |
| M-02 | Восстановление `in_flight` | При старте операции без `ack_at` возвращаются в `pending` |
| M-03 | Проверка целостности | Контрольная сумма последней транзакции; карантин при расхождении |
| M-04 | Аварийный экспорт | JSON всех несинхронизированных данных, доступен офлайн (FR-JRN-33) |
| M-05 | Ранняя синхронизация | Попытка отправки при каждом удобном случае; подсветка «несинхронизировано > 2 ч» |

| M-07 | Постоянное хранилище | `persist()` и проверка `persisted()` |

## 12. Развёртывание

- Среды: `dev`, `stage`, `prod`; изоляция данных.
- CI/CD: сборка → тесты → e2e → артефакты → staged rollout (5/25/100%) → откат.
- Blue-green для сервера, откат ≤ 10 минут.
- Версионирование API `/v1`, поддержка 2 мажорных версий клиента 90 дней.
- Feature flags: голос, Web Speech, фото, push, серверный поиск, классы устройств.
- Бэкапы: ежедневно, 30 дней, проверка восстановления ежеквартально.

## 13. Отказоустойчивость и деградация

| Отказ | Поведение |
|---|---|
| Нет сети | Полная локальная работа, баннер, очередь |
| Сервер 5xx | Backoff, статус «Сервер недоступен», данные не теряются |
| 401 | Refresh; при неудаче — «Требуется вход», запись доступна |
| Нет квоты | Предупреждение, очистка кэшей, экспорт, запись блокируется только при отказе IDB |
| Нет микрофона/модели | Ручной ввод или Web Speech |
| Нет памяти для ASR | Деградация до класса C |
| Повреждение IDB | Экспорт, переинициализация, повторная синхронизация |
| Нет Background Sync | Синхронизация при открытии/фокусе |
| Устаревший курсор | Полный resync |

## 14. Ограничения архитектуры

1. Один наряд на запись (MVP).
2. Один активный sync на устройство.
3. Офлайн-сессия 30 дней; после — только чтение и экспорт.
4. Админ-панель требует сети.
5. Нет шифрования локальной БД в MVP.
6. Нет реального времени: изменения появляются после синхронизации.
7. Максимум 50 операций в батче; 10 000 операций в очереди — верхняя граница.
