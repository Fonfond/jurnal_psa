## 1. Резюме

Строим монолитное приложение из трёх частей: PWA-клиент (React + IndexedDB), REST/Sync API (`/v1`) и PostgreSQL. Основной сценарий — офлайн-создание записи, очередь операций, серверный merge, `change_log`, идемпотентность.

Итерации:

1. **Шаг 1 (этот документ)** — бриф и план.
2. **Шаг 2** — каркас репозитория, окружение, миграции, локальное хранилище, seed.
3. **Шаг 3** — API: auth, журнал, sync, merge, permits, audit, admin.
4. **Шаг 4** — клиент: экраны, офлайн-очередь, синхронизация, статусы.
5. **Шаг 5** — тесты, запуск, трассируемость, отчёт.

**Границы первой рабочей версии:** журнал (создание/просмотр/правка/удаление), очередь и синхронизация, merge C-01…C-12, наряды из CSV, проверка записи, аудит, базовое администрирование. Голос — только интерфейс и адаптер с ручным режимом: on-device ASR включается после гейта G1.

## 6. Потоки синхронизации

### 6.1. Запись

```
UI → Domain.validate (Zod) → Dexie tx:
     entries.put + outbox.put + revisions.put
   → optimistic status=pending
   → SyncEngine.wake()
```

### 6.2. Push

```
POST /v1/sync/push {device_id, app_version, ops[]}
  1. auth + CSRF + права
  2. для каждой op:
     - idempotency: есть op_id → вернуть сохранённый ответ (duplicate=true)
     - базовая валидация payload (Zod)
     - загрузить текущую сущность
     - version == base_version → применить
     - иначе → merge по C-01…C-12
     - записать revision, version+1, change_log, audit
     - сохранить ответ в idempotency
  3. вернуть results[] + server_time
```

**Порядок:** все операции одной сущности — в одном батче; при > 50 — последовательные батчи. Параллелизм ≤ 3 только между сущностями.

### 6.3. Changes

```
GET /v1/sync/changes?since_seq=N&limit=200
  → выборка change_log.seq > N с учётом области видимости роли
  → upsert/tombstone, permits, entries
  → next_seq, has_more
```

Справочники — только через `/dictionaries/snapshot`.

### 6.4. Merge

Сервер — авторитетный: сравнивает `field_clocks` с текущими HLC, применяет правила C-01…C-12, сохраняет проигравшее в `entry_revisions`, возвращает `merged_entry`, `resolution`, `conflicts[]`. Клиент не сливает.

**Правила:** проверенная запись блокирует правку автора; удаление vs изменение — по HLC; неоднозначность — `conflict` и ручной разбор.

### 6.5. Идемпотентность

`idempotency_records` хранит ответ 30 дней. Повтор возвращает текущее состояние и `duplicate=true`.

### 6.6. HLC

```
physical = max(now, last_physical)
counter  = physical == last_physical ? counter+1 : 0
format   = pad13(physical) + ':' + pad5(counter) + ':' + node8
```

Дрейф > 5 мин → `clock_anomaly`; порядок определяет сервер.

## 7. Клиент (offline-first)

### 7.1. Слои

- `screens` — S-01…S-15.
- `db` — Dexie, репозитории, транзакции.
- `sync` — очередь, отправка, изменения, backoff, Web Locks.
- `api` — fetch с cookie и CSRF.
- `app` — роутинг, layout, статус-бар.

### 7.2. Очередь

- `outbox` с `op_id`, `entity_id`, `op_type`, `payload`, `field_clocks`, `hlc`, `base_version`, `attempts`, `next_attempt_at`.
- Восстановление `in_flight` → `pending` при старте.
- Backoff 2–15 мин, 10 попыток, `dead` для неисправимых.
- Индикатор: «Ожидает N», «Синхронизировано», «Ошибка», «Конфликт».

### 7.3. Триггеры

Старт, `online`, фокус (≤ 1 раза в 30 с), таймер 5 мин, Web Locks, Background Sync (Chrome), Periodic Sync (Chrome, установленное PWA).

### 7.4. Экраны первой версии

S-01 вход, S-02 лента, S-03 создание, S-05 карточка, S-06 правка, S-07 наряды, S-09 фильтры, S-10 синхронизация, S-11 профиль, S-13 конфликт, S-15 офлайн. Админ — минимальный S-14.

### 7.5. PWA

Manifest, standalone, иконки, precache ≤ 600 КБ, network-only для API, offline fallback, обновление после опустошения очереди.
